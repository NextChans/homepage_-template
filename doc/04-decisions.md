## ADR-001. `apple-design` 스킬을 프로젝트 레벨로 설치

- **맥락** 사용자가 "apple-design 스킬을 설치한 후 사용"을 요구. 사내/마켓플레이스 카탈로그에
  동명 스킬이 없었다.
- **결정** `schhaohao/apple-design` 의 `SKILL.md` 를 `.claude/skills/apple-design/` 에 그대로 복사.
  출처·설치일·대안 스킬을 `SOURCE.md` 에 기록.
- **근거** 후보 6개 중 frontmatter 규격이 올바르고(`name: apple-design`) 내용이 자체 완결적이며
  외부 참조 파일이 없는 유일한 저장소. 프로젝트 레벨이면 저장소를 클론한 누구나 같은 규범을 받는다.
- **대안** `chaos-xxl/apple-design-skill` (토큰/레이아웃 레퍼런스가 더 상세하지만 `prompts/` 분산
  구조라 그대로 스킬로 동작하지 않음), `tristan-mcinnis/apple-hig-designer-skill-2026` (HIG/네이티브 중심).
- **남는 위험** 원본 frontmatter 가 `LICENSE.txt` 를 참조하지만 저장소에 라이선스 파일이 없다.
  **사내 배포·재배포 전 원저작자에게 라이선스를 확인해야 한다.** 서브모듈이 아니라 복사이므로
  업스트림 변경은 자동 반영되지 않는다.

## ADR-002. 웹폰트를 쓰지 않고 시스템 폰트 스택 사용

- **결정** `-apple-system` → `SF Pro` → `Pretendard` → `Apple SD Gothic Neo` → `system-ui`
- **근거** apple-design 스킬이 시스템 폰트 스택을 최우선으로 요구한다. 부수 효과로 웹폰트 요청이
  0건이 되어 LCP 가 개선되고 CLS 가 발생하지 않는다.
- **남는 위험** Windows/Android 에서는 SF Pro 가 없어 `Malgun Gothic` / 기본 산세리프로 떨어진다.
  브랜드 일관성이 중요해지면 Pretendard 를 self-host 하는 방안을 재검토한다(폰트 용량 트레이드오프).

## ADR-003. Server Component 우선, 클라이언트는 3개 컴포넌트로 제한

- **결정** `site-header`, `reveal`, `contact-form` 만 `'use client'`.
- **근거** 마케팅 사이트는 상호작용이 적다. 정적 프리렌더로 공유 청크 약 102 kB 수준을 유지.
- **남는 위험** 향후 애널리틱스·챗 위젯을 붙이면 이 수치가 무의미해진다. 서드파티 스크립트는
  `next/script` 의 `lazyOnload` 로 넣고 번들 영향을 매번 측정한다.

## ADR-004. 문의 저장은 Server Action + `service_role`, RLS 정책 없음

- **맥락** 문의 데이터에는 개인정보(이름·이메일·연락처)가 들어간다.
- **결정** `inquiries` 테이블에 RLS 를 켜고 **정책을 만들지 않는다.** anon 키로는 어떤 작업도
  불가하고, 삽입은 `service_role` 을 쓰는 Server Action 에서만 수행한다.
- **근거** anon insert 정책을 열면 anon 키만으로 임의 데이터 삽입이 가능해진다(키는 공개된다).
  금융 도메인에서 개인정보 테이블에 공개 쓰기 경로를 두는 것은 허용하지 않는다.
- **대안** anon insert 정책 + Turnstile/reCAPTCHA. 서버를 거치지 않아 간단하지만,
  검증 로직이 클라이언트로 나가고 스팸 대응이 외부 서비스 의존이 된다.
- **남는 위험** `service_role` 키 유출 시 전체 DB 가 노출된다. `'server-only'` 로 클라이언트
  번들 유입을 막았고 `NEXT_PUBLIC_` 접두어를 금지했지만, **배포 플랫폼의 환경변수 관리와
  키 로테이션 정책이 별도로 필요하다.**

## ADR-005. IP 는 원문 대신 salt 적용 해시만 저장

- **결정** `INQUIRY_IP_HASH_SALT` + SHA-256 → `ip_hash`. salt 가 없으면 해시조차 저장하지 않는다.
- **근거** 어뷰징 억제에는 동일성 판별만 필요하고 원문은 불필요하다. IPv4 공간은 작아
  salt 없는 해시는 전수 대조로 재식별이 가능하므로, salt 부재 시 저장을 포기하는 쪽을 택했다.
- **남는 위험** salt 를 교체하면 기존 해시와 매칭이 끊겨 레이트리밋 이력이 초기화된다.
  의도된 동작이다.

## ADR-006. 레이트리밋을 DB 카운트 기반으로 구현

- **결정** 동일 `ip_hash` 기준 10분 내 3건 초과 차단. 카운트 조회 실패 시에는 **접수를 막지 않고**
  로그만 남긴다.
- **근거** 외부 의존(Redis)을 늘리지 않고 어뷰징을 억제하는 최소 구성. 정합성보다 가용성을
  택한 것은 이 데이터가 결제 원장이 아니라 문의 접수이기 때문이다.
- **남는 위험** 동시 요청에서 원자적이지 않아 순간적으로 한도를 넘을 수 있다.
  트래픽이 커지면 Upstash Redis 등 외부 카운터로 이동한다.

## ADR-007. 스크롤 리빌에 `<noscript>` 폴백을 추가

- **맥락** 구현 직후 스크린샷에서 본문이 전부 빈 화면으로 나왔다. 원인은 캡처 스크립트의
  smooth scroll 이었으나, 이 과정에서 **JS 미실행 시 `.reveal` 이 콘텐츠를 영구히 숨긴다**는
  실제 결함이 드러났다.
- **결정** `app/layout.tsx` `<head>` 에 `<noscript>` 스타일을 넣어 `.reveal` 을 강제 표시.
  `reveal.tsx` 에도 `IntersectionObserver` 부재 시 즉시 표시 경로를 유지.
- **근거** 마케팅 사이트에서 본문이 안 보이는 것은 치명적이다. HTML 에는 SSR 되어 있으므로
  크롤러에는 영향이 없었지만, JS 차단 환경의 실사용자에게는 백지가 된다.

## ADR-008. `Hero` 에 `size` 프롭을 도입 (한국어 타이포 대응)

- **맥락** `.type-display`(최대 6rem)를 하위 페이지 히어로에 적용하니 한국어 헤드라인이
  3줄로 깨지고 여백 균형이 무너졌다(스크린샷으로 확인).
- **결정** `size: 'display' | 'headline'`. 홈만 `display`, 나머지는 `headline`.
- **근거** 한국어는 라틴 문자보다 자폭이 넓다. 스케일을 그대로 이식하면 Apple 원본의
  "한 문장이 화면을 지배하는" 효과가 오히려 깨진다.

## ADR-009. Supabase 환경변수 이름을 두 체계 모두 지원

- **맥락** Vercel 배포를 붙이려고 확인해 보니, Vercel 의 Supabase Marketplace 연동이 주입하는
  변수명이 우리 `.env.example` 과 달랐다. 연동은 `SUPABASE_URL` / `SUPABASE_SECRET_KEY` 를
  넣고, 우리가 읽던 `SUPABASE_SERVICE_ROLE_KEY` 와 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 는
  넣지 않는다. 그대로 두면 **연동을 켜도 앱은 "미설정" 상태로 조용히 동작**한다.
- **또 하나** Supabase 는 레거시 `anon` / `service_role` JWT 를 신형
  `sb_publishable_...` / `sb_secret_...` 로 대체하며 레거시는 2026년 말 지원 종료 예정이다.
- **결정** `lib/supabase/server.ts` 가 우선순위 배열로 두 체계를 모두 찾는다.
  - URL: `NEXT_PUBLIC_SUPABASE_URL` → `SUPABASE_URL`
  - 비밀키: `SUPABASE_SECRET_KEY` → `SUPABASE_SERVICE_ROLE_KEY`
  신형을 먼저 본다. 읽는 지점은 여전히 이 파일 한 곳뿐이다.
- **근거** 이름을 한쪽으로 고정하면 (a) 연동 방식을 바꿀 때마다 코드를 고쳐야 하고
  (b) 레거시 키 종료 시 다시 고쳐야 한다. 배열 두 개로 양쪽을 흡수하는 비용이 훨씬 낮다.
- **대안** Vercel 쪽에서 변수명을 우리 이름으로 다시 매핑 — 대시보드에 숨은 설정이 늘어나고
  저장소만 봐서는 알 수 없게 된다. 채택하지 않았다.
- **남는 위험** 두 이름이 동시에 존재하고 값이 다르면 신형이 조용히 이긴다. 의도한 동작이지만,
  키를 교체할 때 옛 이름을 지우지 않으면 혼란이 생길 수 있다.

## ADR-010. 개발 안내 배너를 NODE_ENV 로 차단

- **맥락** `/contact` 에는 Supabase 미설정 시 "환경변수가 없다"는 개발용 배너가 있었고,
  제거는 `doc/05-content-guide.md` 의 수동 체크리스트에 맡겨져 있었다.
- **결정** `process.env.NODE_ENV === 'production'` 이면 렌더링하지 않는다.
- **근거** 수동 체크리스트는 잊힌다. env 주입이 실패한 채로 배포되면 방문자에게 내부 설정
  정보가 노출된다. 코드로 막는 편이 확실하다.
- **부수 효과** 프로덕션에서 배너가 안 보이는 것이 정상 동작이 되므로, env 주입 실패는
  배너가 아니라 **서버 로그(`supabaseConfigHint()`)와 실제 제출 테스트**로 확인해야 한다.
  `doc/09-deployment.md` 검증 체크리스트에 그렇게 적었다.

## ADR-011. Supabase 리전 서울 확정, Vercel 함수 리전을 `vercel.json` 에 고정

- **맥락** Supabase 프로젝트 리전이 서울(`ap-northeast-2`)로 확정됐다. 그런데 **Vercel 함수의
  기본 리전은 `iad1`(버지니아)** 이다. 그대로 두면 문의 제출마다 서울 DB ↔ 미국 함수를
  왕복해 Server Action 지연이 크게 늘어난다.
- **결정**
  1. ~~`vercel.json` 에 `{"regions": ["icn1"]}` 을 넣는다.~~ → **철회. 아래 개정 참고.**
     함수 리전은 Vercel 대시보드(Settings → Functions)에서 Seoul(`icn1`)로 설정한다.
  2. `app/privacy/page.tsx` 4항에 보관 리전을 서울로 명시한다.
  3. 국외 이전은 **"해당 없음" 으로 단정하지 않는다.** "검토 진행 중" 으로 표기한다.
- **근거 (1)** 대시보드 설정은 저장소만 봐서는 알 수 없고 누가 언제 바꿨는지도 남지 않는다.
  설정 파일에 두면 리뷰 대상이 되고 리전 변경이 diff 에 남는다. 앞서 ADR 없이 `vercel.json` 을
  만들지 않았던 이유는 리전 코드를 검증하지 못했기 때문이고, 이제 확인했다.
- **근거 (3)** 저장 리전이 국내여도 수탁자 Supabase Inc. 는 국외 법인이다. Supabase 공식
  문서는 primary Postgres/Auth/Storage 는 선택 리전에 머문다고 하면서도, **백업·로그·외부
  시스템 반출·Edge Function 실행·재위탁 업체(sub-processor)가 data residency 와 국외이전
  판단에 영향을 줄 수 있다**고 명시한다. 이 상태에서 방침에 "국외 이전 없음" 을 쓰는 것은
  검증되지 않은 법적 단정이고, 금융 도메인에서는 그 자체가 리스크다.
- **대안** 함수 리전을 대시보드에서만 설정 — 채택하지 않음(위 근거 1). 방침에 "국외 이전 없음"
  단정 — 채택하지 않음(위 근거 3).
- **남는 위험**
  - 요금제에 따라 함수 리전 선택이 제한될 수 있다. 배포가 거부되면 `regions` 를 지우고
    대시보드에서 설정한다. 기능 영향은 없고 지연만 늘어난다.
  - 대시보드 리전과 실제 Supabase 리전이 어긋나도 **아무 에러가 나지 않는다.**
    조용히 느려질 뿐이다. 리전을 바꿀 때 두 곳을 함께 확인해야 한다.

### 개정 (2026-09-10) — `vercel.json` 철회

`vercel.json` 을 추가한 커밋(`bdf8af7`)의 Vercel 배포가 33초 만에 실패했다. 배포 로그는
Vercel 토큰이 없어 확인할 수 없었다.

배제한 가설:

- **요금제 제약** — [Hobby 도 단일 리전은 선택 가능](https://vercel.com/changelog/hobby-customers-can-now-select-their-preferred-region-for-serverless)
  하고 우리는 `icn1` 하나만 지정했다. 가능성 낮음.
- **설치 실패** — `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD` / `PLAYWRIGHT_BROWSERS_PATH` 없이
  깨끗한 디렉터리에서 `npm ci` 를 재현했고 29초에 exit 0. 설치 문제가 아니다.

남은 것은 `vercel.json` 자체(스키마 검증 등) 또는 vercel.json 과 무관한 원인이다.
로그 없이 확정할 수 없으므로 **배포에 영향을 주는 유일한 변경을 되돌려 변수를 제거**했다.

- 다음 배포가 성공하면 원인은 `vercel.json` 이었고, 리전은 대시보드에서 설정한다.
- 다음 배포도 실패하면 원인은 다른 곳이며 Vercel 배포 로그가 필요하다.

**교훈**: 배포 설정을 저장소에 넣는 판단(리뷰 가능성)은 유효하지만, **직접 배포를 검증할 수단이
없는 상태에서 배포 파이프라인 설정을 추가하면 안 된다.** 검증 수단이 먼저다.

## ADR-012. 환경변수에서 온 URL 은 반드시 검증한다 (Vercel 배포 9회 실패의 원인)

- **증상** Vercel 배포가 **9회 연속 실패**. 같은 커밋에서 GitHub Actions CI 는 매번 통과.
  문서 1개만 바꾼 커밋도 실패. `vercel.json` 제거, `next` 업그레이드, `engines.node` 고정
  모두 무효(ADR-011 개정 참고).
- **실제 원인** 빌드 로그의 결정적 한 줄:
  ```
  [Error: Failed to collect configuration for /_not-found]
    [cause]: TypeError: Invalid URL
  ```
  `content/site.ts` 가 `process.env.NEXT_PUBLIC_SITE_URL ?? '...'` 였고,
  `app/layout.tsx` 가 그 값을 `metadataBase: new URL(site.url)` 로 썼다.

  **`??` 는 null/undefined 만 폴백한다. 빈 문자열은 통과시킨다.**
  Vercel 은 미설정 `NEXT_PUBLIC_*` 를 **빈 문자열로 주입**하므로 `site.url === ''` 이 되고,
  `new URL('')` 이 TypeError 를 던져 `Collecting page data` 단계에서 빌드가 죽었다.

  로컬·CI 는 변수가 **아예 없어서**(`undefined`) `??` 가 정상 동작해 통과했다.
  이 한 칸 차이가 "CI 통과 · Vercel 실패" 의 전부였다.
- **재현** `NEXT_PUBLIC_SITE_URL="" npm run build` → 동일한 에러. 미설정으로는 재현되지 않는다.
- **결정**
  1. `content/site.ts` 에 `resolveSiteUrl()` 을 두고 **trim → 빈 값 검사 → `new URL` try/catch →
     프로토콜 검사 → 끝 슬래시 제거** 를 거친 값만 내보낸다. 어떤 입력에도 throw 하지 않는다.
  2. **CI 의 빌드 스텝에 `NEXT_PUBLIC_SITE_URL: ''` 를 명시적으로 설정한다.**
     Vercel 과 같은(더 엄격한) 조건으로 빌드해, 같은 부류의 회귀가 CI 를 통과할 수 없게 한다.
- **근거** 1번만 고치면 이 버그는 잡히지만 **같은 부류는 또 발생한다.** 환경변수는 "없음" 과
  "빈 값" 이 다르고, 플랫폼마다 어느 쪽을 주는지가 다르다. CI 가 느슨한 조건으로만 검증하면
  배포에서만 깨지는 상황이 반복된다. 그래서 검증 환경 자체를 엄격한 쪽에 맞췄다.
- **교훈 (진단 과정)**
  - 가설 두 개(`vercel.json`, Node 버전)를 각각 푸시로 검증했고 **둘 다 틀렸다.**
    로그 한 줄이 그 모든 추측보다 결정적이었다. **로그 확보를 더 일찍, 더 강하게 요구해야 했다.**
  - "CI 는 통과하는데 배포만 실패" 는 소스 문제가 아니라 **환경 차이** 신호다.
    그 방향으로 좁히는 건 맞았지만, 환경 차이의 후보에 **환경변수의 빈 값 주입**을 넣지 못했다.
  - 소요 시간이 35~42초로 일정했던 것은 실제로 **빌드가 거의 끝난 뒤**(Compiled successfully →
    Collecting page data) 죽었기 때문이다. "빌드 후 단계 실패" 라는 재해석은 방향이 맞았다.

## ADR-013. 사이트 절대 URL 을 server-only 모듈로 분리하고 Vercel 도메인을 자동 사용

- **맥락** 머지 후 Production(`homepage-template-ivory.vercel.app`)을 검증하니 라우트·보안은
  전부 정상이었으나 **`sitemap.xml` 과 `robots.txt` 의 절대 URL 이 플레이스홀더
  `https://www.example.co.kr`** 로 나갔다. `NEXT_PUBLIC_SITE_URL` 을 설정하지 않았기 때문이다.
  ADR-012 의 수정은 빌드가 깨지는 것만 막았고, **조용히 틀린 SEO 데이터가 나가는 것**은
  그대로였다.
- **문제 2 (잠재)** URL 해석이 `content/site.ts` 에 있었는데, 이 모듈은 클라이언트 컴포넌트
  (`components/site-header.tsx`)도 import 한다. `NEXT_PUBLIC_` 이 아닌 환경변수는 클라이언트
  번들에서 사라지므로 **같은 `site.url` 이 서버에선 실주소, 클라이언트에선 플레이스홀더**가
  된다. 지금은 클라이언트에서 렌더링하지 않아 드러나지 않지만, 누가 쓰는 순간 조용한
  hydration 불일치가 된다.
- **결정**
  1. `lib/site-url.ts` 를 만들고 `import 'server-only'` 를 선언한다. `siteUrl` 을 여기서만
     내보내고 `content/site.ts` 에서 `url` 을 제거한다. → 경계를 **빌드 타임에 강제**한다.
     (`metadataBase`·`sitemap`·`robots` 는 모두 서버 전용이라 제약이 아니다.)
  2. 해석 우선순위를 3단으로 둔다.
     `NEXT_PUBLIC_SITE_URL` → `VERCEL_PROJECT_PRODUCTION_URL` → 플레이스홀더.
  3. 스킴이 없으면 `https://` 를 붙인다.
     [`VERCEL_PROJECT_PRODUCTION_URL` 은 스킴 없이 오고, 프리뷰 배포에도 항상 주입되며
     OG·metadataBase 용도로 문서화되어 있다](https://vercel.com/docs/environment-variables/system-environment-variables).
- **근거** 사람이 잊을 수 있는 설정은 **플랫폼이 이미 아는 값으로 자동 채우는 편이 낫다.**
  1번 우선순위를 유지하므로 실도메인이 생기면 그것이 항상 이긴다. 플레이스홀더는 로컬
  개발용으로만 남는다.
- **대안** Vercel 대시보드에 `NEXT_PUBLIC_SITE_URL` 을 수동 입력 — 동작하지만 잊으면 다시
  조용히 틀린다. `doc/05-content-guide.md` 체크리스트에만 의존하는 방식이 이미 한 번 실패했다.
- **남는 위험** Vercel 이 아닌 호스팅에서는 2번이 없으므로 플레이스홀더로 떨어진다.
  `isPlaceholderSiteUrl` 을 함께 내보내 향후 경고·헬스체크에 쓸 수 있게 했다.
- **검증** 빌드 5조건(둘 다 미설정 / 빈 문자열 / 잘못된 형식 / VERCEL 변수만 / 빈 값+VERCEL)
  모두 통과. Vercel 환경 모사 시 sitemap·robots 가 실제 도메인으로 출력.

## ADR-014. 상담 폼·개인정보처리방침을 기능 플래그로 내리고, 실적 수치를 플레이스홀더로 치환

- **맥락** 사이트가 공개된 상태에서 세 가지가 리스크로 남아 있었다.
  1. 근거 없는 실적 수치(`320+`, `12,000대`, `96%` 등) — 표시광고법 리스크
  2. 개인정보처리방침이 초안 — 국외이전 등 확정된 내용이 없음
  3. 보관기간 3년을 방침에 적었으나 삭제 잡이 없음 — 그 자체가 위반
  사용자 결정: **수치는 플레이스홀더로 치환, 방침은 비공개, 상담 접수는 내리고
  전화·이메일로만 받는다. 접수 알림은 Slack 으로 구성만 해둔다. 나중에 재활성화한다.**
- **결정 (1) 삭제가 아니라 기능 플래그** — `content/features.ts` 에
  `inquiryForm` / `privacyPolicy` 두 개를 둔다.
  - **환경변수가 아니라 코드 상수**로 둔 이유: 켜고 끄는 판단이 컴플라이언스 결정이다.
    대시보드에서 조용히 바뀌면 안 되고 PR 로 검토·기록되어야 한다. 재활성화는 한 줄 변경.
  - **타입을 `boolean` 으로 명시**한 이유: `as const` 면 리터럴 `false` 로 좁혀져
    **비활성 분기가 죽은 코드가 되어 타입 검사·린트에서 빠진다.** 나중에 켤 코드가
    검사받지 못하는 상태로 방치되면 켜는 순간 깨진다.
  - 각 플래그 주석에 **켤 때 함께 해야 하는 일**을 열거했다(방침 확정, 삭제 잡, 알림, env).
- **결정 (2) Server Action 도 서버에서 차단** — UI 를 숨기는 것만으로는 부족하다.
  Server Action 은 모듈 그래프에 포함되면 고유 id 로 등록되어 **폼 없이도 직접 POST 될 수
  있다.** 폼을 내린 동안 개인정보 저장 경로가 열려 있으면 "수집하지 않는다" 는 전제가
  깨진다. `submitInquiry` 첫 줄에서 플래그를 검사해 차단하고, 빌드 산출물
  (`.next/server/app/contact/page.js`)에 그 코드가 포함됨을 확인했다.
- **결정 (3) 실적 수치는 지우지 않고 플레이스홀더로** — `XXX+`, `X,XXX대`, `OO`, `OOOO`.
  섹션 구조와 레이아웃을 유지해 실제 값이 들어올 자리를 남긴다. 근거를 확보하지 못한
  항목은 **숫자를 만들지 말고 배열에서 제거**하라고 주석에 명시했다.
  회사 연혁(연도)도 실적 주장이므로 함께 치환했다.
- **결정 (4) Slack 알림은 배선만** — `lib/notify/slack.ts`.
  `SLACK_INQUIRY_WEBHOOK_URL` 미설정이면 조용히 건너뛰고, 실패해도 **절대 throw 하지
  않는다**(알림 실패가 접수 실패가 되면 안 된다).
  **개인정보를 Slack 으로 보내지 않는다** — Slack 은 제3자이고 메시지는 워크스페이스에
  장기 보존·검색된다. 이름·이메일·연락처·본문을 넣으면 개인정보 처리 위탁 범위가 Slack
  까지 확대되어 방침의 수탁자 목록에 Slack 을 추가해야 한다. 알림에는 분야·회사명·행 id
  만 담고 실제 내용은 Supabase 에서 본다.
- **알려진 비용** 플래그가 꺼져 있어도 폼의 클라이언트 JS(약 32kB)가 `/contact` 방문자에게
  내려간다. 플래그가 `boolean` 이라 번들러가 제거하지 못하고, 서버 컴포넌트에서
  `await import()` 로 바꿔도 Next 의 클라이언트 참조 그래프에 남아 **효과가 없음을
  실측으로 확인**했다(31.8kB 그대로). 라우트를 분리하면 떼어낼 수 있으나 재활성화 비용이
  커진다. **보안 문제는 아니다** — 쓰기 경로는 결정 (2) 로 막혀 있다. 현재는 감수한다.
- **남는 위험** 방침을 비공개로 둔 상태는 **개인정보를 수집하지 않는 동안에만 성립한다.**
  `inquiryForm` 을 켜면서 `privacyPolicy` 를 켜지 않으면 위반이다. 플래그 주석과
  `doc/06-security-compliance.md` 양쪽에 명시했으나 **코드로 강제하지는 않았다.**
- **검증** typecheck·lint·build 통과. 실제 서버 기동 후 `/contact` 에 input/textarea 0개,
  '전화 걸기' 노출, `/privacy` 404, sitemap 에서 `/privacy` 제외, robots 의 disallow 제거 확인.

## ADR-015. 관리자 조회 화면을 Supabase Auth 대신 자체 ID/PW 로 지킨다

- **맥락** 상담 접수는 플래그로 내려둔 상태(ADR-014)지만, 재활성화하면 `inquiries` 에
  개인정보가 쌓인다. 지금까지 조회 경로는 Supabase 대시보드뿐이었고
  `doc/06-security-compliance.md` 에 "**관리자 조회 경로 없음 — 만들 경우 인증 + 접근 감사
  로그를 함께 설계한다**" 로 남아 있었다. 사용자 요청: **ID/PW 로 로그인해서 DB 내용을
  조회할 수 있는 관리자 페이지.**

- **결정 (1) Supabase Auth 를 쓰지 않는다** — 이 프로젝트의 핵심 불변식은
  `inquiries` 가 **RLS on + 정책 0개**(= service_role 전용)라는 것이다.
  Supabase Auth 를 도입하면
  1. 클라이언트에 publishable 키가 나가고,
  2. 로그인한 사용자가 데이터를 읽으려면 `authenticated` 롤에 **정책을 열어야** 한다.
  정책을 한 번 열면 "브라우저에서 도달 가능한 읽기 경로가 없다" 는 전제가 깨진다.
  운영자가 1명인 지금 그 대가를 치를 이유가 없다. **인증만 자체 구현하고 데이터 접근은
  계속 서버에서만 한다.**

- **결정 (2) 자격증명이 없으면 라우트가 존재하지 않는다** — 별도 기능 플래그
  (`content/features.ts`)를 두지 않았다. `ADMIN_USERNAME` / `ADMIN_PASSWORD_HASH` /
  `ADMIN_SESSION_SECRET` **세 개가 모두 있어야** 활성화되고, 하나라도 없으면
  `/admin`·`/admin/login`·`/admin/<id>` 가 전부 `notFound()` 다.
  - 플래그를 켜고 자격증명을 잊는 조합(= 인증 없는 관리자 화면)이 **구조적으로 불가능**하다.
  - 로그인 화면 자체가 없으므로 정찰 대상도 없다.
  - **비밀번호 평문을 환경변수에 두지 않는다.** `scripts/hash-admin-password.mjs` 로
    scrypt 해시(`scrypt$<salt>$<hash>`, N=16384)를 만들어 그 결과만 저장한다.

- **결정 (3) 세션은 서명 쿠키. 서버 세션 테이블을 만들지 않는다**
  - 토큰 = `base64url(payload).base64url(HMAC-SHA256)`, 유효기간 8시간(개인정보 화면이라 짧게).
  - **서명을 먼저 검증하고 그 다음에 payload 를 파싱한다.** 순서가 바뀌면 위조 입력이
    파서에 먼저 닿는다.
  - 쿠키: `httpOnly` + `sameSite=strict` + 프로덕션 `secure` + `path=/admin`.
    `path` 를 좁혀 공개 페이지 요청에 관리자 쿠키가 실려 나가지 않게 한다.
  - **대가: 원격 강제 로그아웃이 불가능하다.** 유출된 쿠키는 8시간까지 유효하다.
    무효화가 필요하면 `ADMIN_SESSION_SECRET` 을 교체한다(= 전체 세션 즉시 만료).
    이 회전 절차를 `doc/10-admin.md` 에 적었다.

- **결정 (4) 가드를 레이아웃이 아니라 페이지마다 호출한다** — `lib/admin/guard.ts` 의
  `requireAdminSession()` 을 `app/admin/layout.tsx` 에 두지 않고
  `page.tsx` 3곳에서 각각 호출한다. **App Router 레이아웃은 클라이언트 내비게이션에서
  다시 실행된다는 보장이 없다.** 레이아웃 가드는 "보이는 인증"이지 실제 접근 제어가
  아니다. 레이아웃에는 그 이유를 주석으로 남겼다.

- **결정 (5) 타이밍 차이로 정보를 흘리지 않는다**
  - 아이디가 틀려도 **비밀번호 검증을 항상 수행**한다(더미 해시). 안 하면 응답 시간으로
    아이디 존재 여부가 드러난다.
  - 비교는 `timingSafeEqual`. 길이가 다르면 그 함수가 throw 하므로 HMAC 으로 길이를
    정규화한 뒤 비교한다.
  - 에러 메시지는 **아이디 오류와 비밀번호 오류를 구분하지 않는다.**

- **결정 (6) 브루트포스 차단은 fail-closed** — `admin_audit_log` 의 최근 15분
  `login_failed` 가 5건 이상이면 잠근다. 카운트 조회가 **실패하면 잠그는 쪽으로 기울인다.**
  문의 접수 레이트리밋은 반대로 가용성을 택했는데(접수를 놓치면 사업 손실),
  여기는 개인정보 접근이라 판단을 뒤집었다. **같은 코드처럼 보이는 두 곳의 정책이 다르다는
  점을 주석에 명시했다.**
  - **한계: 잠금은 IP 해시 기준이고, `INQUIRY_IP_HASH_SALT` 가 없으면 해시가 없어
    잠금이 동작하지 않는다.** 관리자 페이지를 켜려면 이 salt 도 함께 설정해야 한다.

- **결정 (7) 읽기 전용 v1** — 스키마에 `status` / `handled_at` / `handled_by` 가 있지만
  변경 UI 를 만들지 않았다. 쓰기를 넣으면 CSRF·권한·변경 이력이 함께 필요해진다.
  상태 변경은 당분간 Supabase 대시보드에서 한다. 화면에도 "읽기 전용" 을 명시했다.

- **결정 (8) 목록에서는 이메일·연락처를 마스킹한다** — 목록은 스캔용이므로 전체 값이
  필요 없다. 상세 화면에서만 원문을 보여주고, 그때 `record_viewed` 를 대상 id 와 함께
  감사 로그에 남긴다. **어깨너머 노출과 스크린샷 유출 면적을 줄이는 것이 목적이며,
  권한 분리가 아니다**(같은 계정이 상세를 볼 수 있다).

- **대안** ① Supabase 대시보드만 사용 — 계정 관리·감사는 Supabase 가 해주지만 운영자에게
  DB 전체 권한을 주게 되고 마스킹·접근 로그를 우리가 통제할 수 없다.
  ② Vercel Password Protection — 유료 플랜이고 감사 로그가 남지 않는다.
  ③ Basic Auth (middleware) — 브라우저 기본 창이라 로그아웃이 없고 실패 잠금도 못 붙인다.

- **남는 위험 (정직하게)**
  1. **공유 ID/PW 하나 + MFA 없음** 으로 고객 개인정보 화면을 지킨다. 운영 인원이 늘거나
     접근 빈도가 높아지면 Supabase Auth + MFA 로 옮겨야 한다. 이것이 이 구성의
     가장 약한 지점이다.
  2. 비밀번호 변경 UI 가 없다 — 환경변수 교체 + 재배포가 필요하다.
  3. 원격 강제 로그아웃 없음(결정 3).
  4. `admin_audit_log` 삭제 잡이 없다. `inquiries` 3년 보관과 별도로 정해야 한다.
  5. 감사 로그 기록 실패가 조회를 막지는 않는다(가용성 우선). 대신 서버 로그에 남긴다.

- **검증** 자격증명 미설정 시 3개 라우트 모두 404 확인. 실제 브라우저(Playwright)로
  전체 흐름 16개 항목 통과 — 미인증 리다이렉트 / 비밀번호 오류 / 아이디 오류(같은 메시지) /
  정상 로그인 / 쿠키 속성 4가지(HttpOnly·SameSite=Strict·path=/admin·만료 8시간) /
  **위조 쿠키 거부** / 로그아웃 시 쿠키 제거. 12자 미만 비밀번호는 해시 스크립트가 거부.

## ADR-016. 키오스크(일반형·베리어프리)를 별도 서비스로 추가하고, 접근성 요건은 단정하지 않는다

- **맥락** 사용자 요청: **"키오스크도 판매하니까 추가"**, 이어서
  **"키오스크는 일반형, 베리어프리도 있다는 걸 같이 기재"**.

- **결정 (1) 밴 단말기 안에 넣지 않고 6번째 서비스로 분리** — 두 제품의 구매 결정 주체와
  검토 항목이 다르다. 밴 단말기는 **직원이 조작**하는 결제 단말이고, 키오스크는
  **고객이 직접 조작**하는 무인 기기다. 키오스크는 설치 실측·접근성 요건·화면 구성이
  따로 붙는다. 카드 하나 안에 두면 두 검토가 섞인다.
  - 배치는 하드웨어끼리 묶어 **2번**(밴 단말기 다음). 그래서 뒤쪽 4종의 `mark` 를
    `03`…`06` 으로 **다시 번호 매겼다.** 순서를 정보 구조에 맞추는 편이,
    번호를 안 건드리려고 맨 뒤에 붙이는 것보다 낫다고 판단했다.
  - 두 서비스가 중복으로 보이지 않게 ① 밴 단말기 `intro` 에서 "무인 키오스크" 문구를
    빼고, ② 키오스크 FAQ 에 **"밴 단말기 서비스와 무엇이 다른가요?"** 를 넣었다.

- **결정 (2) 접근성 요건을 문안에서 단정하지 않는다** — 무인정보단말기 접근성 관련 규정은
  **적용 대상과 시점이 시설 유형·규모에 따라 단계적**이다. 시행일이나 규모 기준을
  카피에 박아 넣으면 곧 틀린 말이 되고, 그 상태로 영업 문안에 남는다.
  - 채택: `적용 대상·시기는 시설 유형과 규모에 따라 다릅니다` + `매장 조건을 확인해
    해당 여부를 먼저 판단해 드립니다` + **최종 판단은 법령·소관 기관 확인을 권한다.**
  - 기각: 근거 조문·시행일·규모 기준을 직접 인용 — 정확해 보이지만 개정에 취약하고,
    확인일자 없이 남으면 오히려 오해를 만든다. `homepage-content` 스킬의
    "법령 요건 수치의 직접 인용" 금지 규칙과 같은 이유다.
  - "설치 의무가 있습니다" 같은 **단정도 쓰지 않았다** — 컨설팅 유인용 단정은
    표시광고법 리스크다.
  - 대신 **제공 산출물**에 `베리어프리 사양 검토`(화면 높이·도달 범위, 음성 안내,
    점자·촉각 키패드, 저시력 대비 화면)를 명시해 **무엇을 해주는지**로 말한다.

- **결정 (3) 서비스 개수에 의존하는 값을 파생값으로 바꿨다** — 5종 → 6종에서
  **두 곳이 조용히 틀어졌다.**
  1. `"다섯 개의 일."` 이 `service-grid.tsx` 와 `app/services/page.tsx` 에 하드코딩.
     → `content/services.ts` 의 `serviceCountKo` 로 통일.
  2. 벤토 그리드에서 **첫 카드가 2칸을 먹으므로** 3열 마지막 행이
     카드 1개 + 빈칸 2개가 됐다.
     → `cardSpan(index, total)` 이 `열 수 - (total % 열 수)` 로 남는 칸을 계산해
       마지막 카드를 늘린다. span 클래스는 **Tailwind 가 스캔할 수 있도록 정적 문자열 맵**
       으로 둔다(문자열 조립하면 클래스가 생성되지 않는다).
  - **근거** 콘텐츠 개수는 앞으로도 변한다. 그때마다 사람이 두 곳을 기억해야 하는 구조를
    남기지 않는다. `homepage-content` 스킬에 이 두 항목을 명시했다.

- **결정 (4) slug 제약을 같은 커밋에서 넓힌다** —
  `20260910000003_inquiries_add_kiosk_slug.sql`. 폼 select 는 `services` 배열을 순회하므로
  **UI 에는 즉시 나타나지만** 제약을 안 넓히면 저장이 실패한다. 즉
  **"선택은 되는데 접수는 실패하는"** 조합이 된다. 지금은 `inquiryForm` 플래그가 꺼져 있어
  실제 저장이 없지만, 재활성화 시점에 빠뜨리지 않도록 지금 넣었다.

- **남는 위험** 키오스크 문안의 사양·소요기간(`표준 2 – 6주`)은 **템플릿용 임시값**이다.
  실제 취급 기종·리드타임으로 교체해야 한다. 베리어프리 사양 항목이 실제 공급 기종의
  스펙과 일치하는지도 대외 공개 전 확인이 필요하다.

- **검증** typecheck·lint·build 통과, `/services/kiosk` SSG 경로 생성 확인.
  라이트·다크·모바일 스크린샷으로 **벤토 그리드 마지막 행에 빈칸이 없음**,
  `"여섯 개의 일."` 반영, 히어로 헤드라인 1줄 유지, 모바일 가로 스크롤 없음 확인.

## ADR-017. 관리자 설정값은 trim 하고, 로그인 실패 원인을 서버 로그로 드러낸다

- **맥락** 관리자 페이지를 실제로 활성화하자 **로그인이 안 됐다.** 화면에는
  `아이디 또는 비밀번호가 올바르지 않습니다` 만 나왔고(의도된 동작), 그래서
  **원인을 좁힐 방법이 전혀 없었다.** 감사 로그의 `actor` 는 *사용자가 입력한* 값이라
  `ADMIN_USERNAME` 설정값과 대조가 되지 않았다.

- **결정 (1) 환경변수는 `trim()` 해서 읽는다** — `adminEnv()` 하나로만 읽는다.
  대시보드에 값을 붙여넣을 때 앞뒤 공백·줄바꿈이 섞이는 것은 흔한 사고이고,
  이 값들은 **사용자 입력이 아니라 우리가 넣은 설정값**이므로 공백을 의미 있는
  문자로 취급할 이유가 없다.
  - **폼으로 들어온 비밀번호는 절대 trim 하지 않는다** — 사용자가 정한 값이고
    공백도 비밀번호의 일부다. 아이디는 설정값과 맞춰야 하므로 trim 한다.
  - **함께 고친 잠재 버그**: `startSession` 이 *제출된* 사용자명을 토큰에 담고
    `readToken` 이 `ADMIN_USERNAME` 과 비교한다. 한쪽만 trim 하면 **발급 직후 세션이
    무효가 되어 로그인 → 리다이렉트 무한 루프**가 된다. `startSession` 이 설정값을
    담도록 바꾸고 인자를 없앴다. 브라우저로 루프가 없음을 확인했다.

- **결정 (2) 화면은 구분하지 않지만 서버 로그는 구분한다** —
  `{ usernameMatched, passwordMatched, storedHashShape }`.
  **비밀값은 출력하지 않는다**(해시는 형태만 설명: 필드수·길이·바이트수).
  사용자명 존재 여부는 화면에서만 숨기면 충분하고, 서버 로그를 볼 수 있는 사람은
  이미 환경변수를 볼 수 있는 사람이다. 이 구분이 없으면 **설정 실수와 침입 시도가
  똑같이 보인다.**

- **결정 (3) 잠금 사유를 `locked` / `unavailable` 로 분리** —
  `isLoginLocked(): boolean` → `loginGate(): 'ok' | 'locked' | 'unavailable'`.
  감사 로그를 조회할 수 없을 때(fail-closed) `로그인 시도가 너무 많습니다` 를 띄우면
  **설정 실수를 브루트포스로 오인하게 만든다.** 테스트 중 실제로 이 메시지에 속아
  시간을 썼다. `unavailable` 은 Supabase 설정과 `admin_audit_log` 테이블을 확인하라고
  직접 말한다. 차단 동작(fail-closed)은 그대로다 — 메시지만 정확해졌다.

- **결정 (4) 자격증명 생성기를 두 번 묻게 바꿨다** — `hash-admin-password.mjs`.
  - 비밀번호를 **인자로 받지 않는다**(`ps`·셸 히스토리 노출). stdin 숨김 입력만.
  - **두 번 입력받아 일치할 때만** 해시를 만들고, 만든 해시로 **자기검증**까지 한다.
    한 번만 묻는 방식은 숨겨진 입력의 오타를 잡을 수 없고, 그 오타가 해시로 굳으면
    배포 후에야 드러난다. **생성 시점에 막는 것이 유일하게 확실하다.**
  - `--verify 'scrypt$...$...'` 모드 추가 — **배포 없이** 비밀번호가 해시와 맞는지
    로컬에서 확인한다. 이번 사고에서 원인을 아이디 쪽으로 좁힌 것이 이 검증이었다.

- **시행착오 기록** 검증 스크립트에서 `readline` 인터페이스를 호출마다 새로 만들어
  **두 번째 입력이 항상 빈 문자열**이 됐다(첫 인터페이스가 스트림을 소비·종료한다).
  테스트에서 `0자` 로 드러나 stdin 을 한 번만 통째로 읽어 줄 단위로 나눠 쓰는 방식으로
  바꿨다. 또 Playwright 테스트가 클릭 후 **303 리다이렉트 완료를 기다리지 않아**
  정상 동작을 실패로 보고했다 — `waitForLoadState('networkidle')` 만으로는 부족하다.
  **코드가 아니라 테스트가 틀린 경우를 먼저 의심해야 했다.**

- **남는 위험** `ADMIN_USERNAME` 을 Secret 으로 저장하면 대시보드에서 값을 다시 볼 수
  없다. 불일치가 의심되면 **삭제 후 재등록**해야 한다. Config 로 바꾸면 확인이 쉬워지지만
  자격증명의 절반이 평문으로 보이므로 Secret 을 유지했다.

- **검증** 공백·줄바꿈을 섞은 환경변수(`ADMIN_USERNAME="testadmin  \n"`, 해시·시크릿
  앞뒤 공백)로 브라우저 **10개 항목 통과** — 로그인 성공 / 리다이렉트 루프 없음 /
  세션 유지 / 아이디 입력 공백 허용 / **비밀번호는 trim 안 함** / 아이디·비밀번호 오류
  모두 동일 메시지 / 위조 쿠키 거부. `unavailable` 경로도 실제 화면 메시지로 확인.
  생성기 6개 경로 확인(일치·불일치·짧은 비밀번호·인자 거부·verify 정상/오답·잘린 해시).

### ADR-017 후속 — 비밀번호 앞뒤 공백을 생성 단계에서 거부한다 (2026-09-10)

trim 수정 배포 후 로그는 `usernameMatched: true, passwordMatched: false,
storedHashShape: 'ok'` 였다. **아이디는 해결됐고 비밀번호만 남았다.**
해시 형태가 정상이므로 붙여넣기 잘림도 아니다.

원인 유형: **해시를 만들 때 쓴 비밀번호에 앞뒤 공백이 있으면 타이핑 로그인은
영구히 실패한다.** 비밀번호 관리자에서 붙여넣으면 공백이 따라오는 경우가 있고,
로컬에서 같은 값을 붙여넣어 검증하면 통과하므로 **검증이 통과하는데도 로그인이
안 되는** 상태가 된다. 서버는 폼으로 들어온 비밀번호를 trim 하지 않는다
(공백도 비밀번호의 일부다 — 이 원칙은 유지한다).

- **생성 단계에서 거부한다.** 경고가 아니라 종료다. 이 상태로 만든 해시는
  쓸 수 없으므로 만들게 할 이유가 없다.
- **`--verify` 가 공백을 지목한다.** 입력값에 공백이 있으면 일치해도 경고하고,
  불일치 시 trim 한 값으로 한 번 더 시도해 "공백을 제거하면 맞습니다" 를 알려준다.
  네 조합(공백해시+공백입력 / 공백해시+깨끗입력 / 정상해시+공백입력 / 양쪽 정상)
  모두 실제로 확인했다.
- **서버 쪽은 바꾸지 않았다.** 입력 비밀번호를 trim 하면 공백을 의도적으로 쓴
  비밀번호를 약화시킨다. 문제는 생성 도구에 있었고 거기서 막는 것이 맞다.

## ADR-018. 관리자 화면에 쓰기를 허용하고, 상태 변경은 별도 이력 테이블에 남긴다

- **맥락** ADR-015 에서 관리자 화면을 **읽기 전용**으로 만들었다. 가동 후 사용자 요청이
  세 가지 들어왔다. ① 상세의 문의 본문이 한 줄로 흘러 화면을 넘어간다
  ② 전화·이메일로 들어온 문의도 직접 등록해 이력을 남기고 싶다
  ③ 처리 상태를 바꾸고, 처리 담당·처리일시도 이력으로 남기고 싶다.
  즉 **읽기 전용 전제를 사용자가 명시적으로 철회했다.**

- **결정 (1) 이력은 컬럼이 아니라 테이블** — `inquiry_status_history` 신설.
  `inquiries.status/handled_by/handled_at` 은 **현재 상태**만 담는다. 덮어쓰면
  "누가 언제 무엇에서 무엇으로 바꿨는지" 가 사라진다. 전자금융 도메인에서 처리 이력이
  없는 상태 변경은 그 자체로 결함이다. 현재 상태는 목록 정렬·필터를 위해 비정규화로
  남기고, 변경은 append-only 로 쌓는다.
  - **등록 시에도 이력 첫 줄(`from_status: null`)을 남긴다.** 이력이 빈 문의를 만들지 않는다.
  - **`on delete cascade`** — 보관기간(3년) 경과로 문의를 삭제하면 이력도 함께 사라져야
    한다. 특정 개인의 업무 맥락이므로 남기면 보관기간 정책이 무의미해진다.
    **`admin_audit_log` 는 반대로 FK 를 걸지 않는다** — 그쪽은 개인정보를 담지 않고
    (`ip_hash` 만) 접근 이력이 더 오래 남아야 한다. 두 테이블의 수명 정책이 다르다.

- **결정 (2) `admin_audit_log` 와 `inquiry_status_history` 를 합치지 않는다**
  - `admin_audit_log`: **관리자가 콘솔에서 무엇을 했는가** (조회 포함, 보안 감사)
  - `inquiry_status_history`: **이 문의가 어떻게 처리되어 왔는가** (업무 이력, 화면 표시)
  목적·수명·노출 대상이 모두 다르다. 하나로 합치면 조회 로그가 업무 화면에 섞이고
  보관기간이 충돌한다.

- **결정 (3) 읽기 모듈과 쓰기 모듈을 분리** — `lib/admin/inquiries.ts`(조회) /
  `lib/admin/inquiry-write.ts`(등록·상태변경). **어떤 코드가 고객 개인정보를 변경할 수
  있는지 import 만 보고 알 수 있어야 한다.** 조회 모듈에 쓰기를 끼워 넣으면 그 경계가
  사라진다.

- **결정 (4) 전화 문의는 이메일이 없다** — `email`/`phone` 의 `not null` 을 풀고
  **`check (email is not null or phone is not null)`** 로 바꿨다. 둘 다 필수로 두면
  담당자가 가짜 이메일을 넣게 되고, 그게 더 나쁘다. 폼에서도 같은 조건을 한국어로 알려준다.

- **결정 (5) 공개 폼 스키마와 직접 등록 스키마를 분리** —
  `lib/inquiry-schema.ts` vs `lib/admin/manual-inquiry-schema.ts`. 규칙이 다르다:
  공개 폼은 연락처 둘 다 필수 + 봇 차단이 필요하고 본인이 동의를 체크한다. 직접 등록은
  연락 수단 하나면 되고 봇 차단이 불필요하며 **관리자가 "동의를 받았음" 을 확인**한다.
  하나로 합치면 어느 쪽 규칙인지 모호해지고, **공개 폼의 필수 조건을 느슨하게 만드는
  방향으로 새어 나간다.**
  - `privacyConsent` 는 양쪽 모두 `literal(true)`. 동의 없이 개인정보를 저장하는 경로를
    만들지 않는다(DB check 제약과 짝).

- **결정 (6) 직접 등록에 관리자 IP 해시를 남기지 않는다** — `ip_hash` 는 문의자의
  유입 추적용이다. 관리자가 입력한 건에 관리자 IP 가 찍히면 문의자 정보로 오해된다.
  등록자는 `created_by`, 접근 기록은 `admin_audit_log` 에 남는다.

- **결정 (7) 문의 원문 수정·삭제는 만들지 않았다** — 접수 원문을 바꾸면 처리 이력의
  근거가 사라진다. 정정이 필요하면 Supabase 대시보드에서 사유를 남기고 처리한다.
  화면에도 그렇게 명시했다.

- **결정 (8) 상세 overflow 는 `min-w-0`** — 문의 본문이 화면을 넘어간 원인은
  `whitespace-pre-wrap` 이 없어서가 아니었다(이미 있었다). **flex 아이템의 기본
  `min-width: auto`** 가 아이템이 내용 최소 폭보다 작아지지 못하게 막아 컨테이너를
  밀어낸 것이다. `min-w-0` + `break-words` 로 해결했다. 같은 실수를 반복하지 않도록
  `Row` 컴포넌트 주석에 이유를 남겼다.

- **남는 위험 (중요)**
  1. **`inquiryForm` 플래그를 끈 이유가 되살아난다.** 공개 폼을 내린 근거는
     ① 처리방침 미확정 ② 3년 보관기간 삭제 잡 없음이었다. 직접 등록은 **같은
     개인정보를 같은 테이블에 쌓는다.** 즉 이 기능을 쓰기 시작하면 삭제 잡과
     처리방침 확정이 **미룰 수 없는 작업**이 된다.
  2. 상태 변경 메모(`note`)는 담당자 자유 입력이다. 개인정보·민감정보가 들어갈 수 있어
     길이 제한과 경고 문구만 두었고 **코드로 막지는 못했다.**
  3. 아직 **단일 공유 자격증명**이다. 누가 등록·변경했는지는 `created_by`/`changed_by` 에
     남지만 전부 같은 계정명이다. 계정·권한 분리가 다음 작업이다.
  4. 이력 기록 실패 시 상태 변경 자체는 되돌리지 않는다(문의를 잃는 것이 더 나쁘다).
     서버 로그로만 드러난다.

- **검증** typecheck·lint·build 통과, `/admin/new` 포함 5개 관리자 라우트 모두 Dynamic.
  실제 브라우저 14개 항목 통과 — 미인증 차단, 로그인, 진입점, 유입 경로 목록(홈페이지 제외),
  **Server Action 직접 검증**(연락 수단 없음 / 동의 미체크 / 본문 10자 미만 / 연락처 형식
  오류 전부 거부), 검증 통과 후 DB 도달, 이메일만으로도 통과. 서버 로그에 입력값(개인정보)
  미노출 확인. 이메일 형식 거부는 브라우저 기본 검증이 먼저 막아 서버까지 도달하지 않으므로
  **스키마 단독 실행**으로 확인했다.
  **DB 가 붙은 상태의 등록·상태변경·이력 적재는 이 환경에서 검증하지 못했다** —
  마이그레이션 적용 후 사용자 환경에서 스모크 테스트가 필요하다.

- **시행착오 (같은 함정을 3번 반복했다)** 관리자 페이지에는 레이아웃 헤더에 로그아웃 폼이
  있어 폼이 2개다. 테스트에서 `button[type="submit"]`.first() 를 눌러 **로그아웃을
  누르고 있었고**, 그 결과 "액션이 실행되지 않는다" 로 보여 가드·쿠키·`secure` 속성까지
  의심하며 오래 헤맸다. 또 클릭 후 303 완료를 기다리지 않아 정상 동작을 실패로 보고했고,
  `type="email"` 을 `setAttribute` 로 벗기려 했으나 React 가 복원해 서버 검증을 확인하지
  못했다. **네 함정 모두 `homepage-verify` 스킬에 기록했다.**
  → 교훈: 실패가 코드 문제로 보일 때 **테스트 하네스를 먼저 의심한다.**

## ADR-019. 계정·권한 시스템 — DB 계정 + 역할 2개 + 환경변수 비상 복구 경로

- **맥락** 사용자 요청: **"관리자, 상담자로 권한을 나누고, 아이디 등록·삭제·비밀번호
  초기화·권한 변경 등 어드민 운영에 필요한 기능들을 추가"** (내가 말한 것 외에도
  필요한 것 포함). 쓰기 기능(ADR-018)이 붙은 뒤로 `created_by`/`changed_by`/`actor` 가
  전부 같은 계정명이라 **개인 책임 추적이 불가능**한 상태였다.

- **결정 (1) ENV 단일 자격증명 → DB 계정 테이블, 그러나 ENV 를 없애지 않는다**
  `admin_users` 테이블을 만들되 `ADMIN_USERNAME`/`ADMIN_PASSWORD_HASH` 는
  **비상 복구(break-glass) 경로로 유지**한다.
  - **이유**: DB 계정이 전부 잠기거나 Supabase 가 죽으면 아무도 못 들어간다.
    계정 관리 화면조차 DB 를 필요로 하므로 "관리자를 전부 비활성화" 같은 실수가
    복구 불가가 된다. ENV 계정은 DB 를 보지 않는 유일한 경로다.
  - 비상 계정은 항상 `admin` 역할, `userId = null`. **화면 헤더에 배지를 계속 표시**
    하고 감사 로그에 `bootstrap(비상 복구 계정)` 을 남긴다 — 일상 업무를 이 계정으로
    하고 있으면 즉시 알아차려야 한다.
  - 로그인은 **DB 계정을 먼저** 시도하고 실패 시 ENV 를 본다. 두 경로 실패 메시지는 동일.

- **결정 (2) 역할 이름이 아니라 권한으로 분기한다** — `lib/admin/roles.ts` 에
  `Permission` 5개(`inquiry.read`/`inquiry.create`/`inquiry.status`/`user.manage`/
  `audit.read`)를 두고 `can(role, permission)` 으로만 판단한다.
  `role === 'admin'` 같은 조건을 코드 전체에 흩뿌리면 역할이 늘 때 전수 조사를 해야 한다.
  - **상담자에게 주지 않은 것**: 계정 관리(스스로 관리자로 승격 가능 → 역할 분리가
    무의미해진다), 감사 로그(감시 대상이 감시 기록을 볼 수 있으면 감사의 의미가 없다).
  - **상담자에게 준 것**: 상태 변경. 상담 업무의 핵심이고 `inquiry_status_history` 에
    이력이 남아 사후 추적이 된다.
  - **권한 부족은 403 이 아니라 `notFound()`** — "여기 관리자 전용 화면이 있다" 는
    사실 자체를 알려줄 이유가 없다.

- **결정 (3) 세션 무효화를 `session_epoch` 로 구현한다 (ADR-015 의 약점 해소)**
  서명 쿠키만으로는 원격 로그아웃이 불가능했다. 세션 테이블을 만드는 대신 계정 행에
  `session_epoch` 를 두고 **토큰에 스냅샷을 담아 매 요청마다 DB 값과 비교**한다.
  다르면 세션을 거부한다. 비밀번호 변경·초기화·강제 만료·비활성화·권한 변경이
  epoch 를 갱신해 **기존 세션을 즉시 무효화**한다.
  - **카운터가 아니라 갱신 시각(Unix 초)을 넣는다.** `epoch = epoch + 1` 은 읽고-쓰는
    두 단계라 동시 요청에서 증가가 유실될 수 있고, **유실되면 무효화해야 할 세션이
    살아남는다.** 시각은 읽지 않고 바로 쓰므로 경쟁이 없다. `bigint` 인 이유는 2038년.
  - **대가**: 매 요청마다 계정 조회 쿼리 1회가 늘어난다. 이미 감사 로그를 쓰고 있어
    추가 왕복 1회의 비용으로 원격 무효화를 얻는 편이 낫다고 판단했다.
  - **권한 변경 시에도 epoch 를 갱신**한다 — 토큰에 담긴 역할이 낡은 값이 되기 때문이다.

- **결정 (4) 삭제보다 비활성화를 기본으로** — 계정을 지우면 `created_by`/`changed_by`/
  감사 로그의 계정명이 무엇을 가리키는지 확인할 수 없게 된다. 비활성화는 로그인만 막고
  이력 해석을 보존한다. 삭제는 남겨두되 **아이디를 정확히 입력하는 확인**을 요구한다.
  - 비활성화는 **세션도 즉시 끊는다.** 상태만 바꾸고 세션을 남기면 최대 8시간 동안
    계속 접근할 수 있다.

- **결정 (5) 자기 자신과 마지막 관리자를 보호한다**
  - 본인 권한 변경·비활성화·삭제 차단: 실수로 자기 접근 권한을 잃으면 되돌릴 수 없다.
  - 활성 관리자가 1명일 때 그 계정의 강등·비활성화·삭제 차단: 계정 관리 화면에 아무도
    못 들어가는 상태를 실수로 만들지 않게 한다(ENV 경로가 있어 완전한 잠금은 아니지만,
    그 경로는 환경변수 접근과 재배포가 필요하다).
  - **활성 관리자 수를 확인할 수 없으면(DB 오류) 진행을 중단한다** — fail-closed.

- **결정 (6) 초기 비밀번호로는 업무를 못 하게 한다** — `must_change_password`.
  관리자가 만든/초기화한 비밀번호 상태에서는 **비밀번호 변경 화면 외의 모든 화면을
  막는다**(가드에서 리다이렉트). 초기 비밀번호가 전달 경로에 남아 있는 동안 실제 업무가
  이뤄지는 상황을 방지한다.
  - 비밀번호 변경 화면은 **별도 가드**(`requireSessionAllowingPasswordChange`)를 쓴다.
    일반 가드를 쓰면 **자신으로 리다이렉트되는 무한 루프**가 된다.

- **결정 (7) 본인 비밀번호 변경 시 현재 비밀번호를 확인한다** — 세션 탈취만으로
  비밀번호를 바꿔 계정을 빼앗지 못하게 한다. 변경 후 **현재 기기의 세션은 재발급**한다
  (epoch 가 바뀌므로 재발급하지 않으면 바꾸자마자 로그아웃된다).

- **결정 (8) 계정 단위 잠금을 IP 단위 잠금과 **함께** 쓴다**
  - IP 잠금(`admin_audit_log` 기반): 한 곳에서 여러 계정을 훑는 시도를 막는다
  - 계정 잠금(`failed_login_count`/`locked_until`): 여러 곳에서 한 계정을 노리는 시도
  둘은 서로 다른 공격을 막으므로 하나로 합치지 않는다.
  - `disabled`/`locked` 는 **비밀번호가 맞은 경우에만** 알려준다. 비밀번호를 모르는
    사람에게는 `invalid` 와 구분되지 않아 계정 존재가 새지 않고, 정당한 담당자에게는
    원인을 알려줄 수 있다.
  - 계정이 없을 때도 **더미 해시로 시간을 쓴다**(`burnPasswordTime`). 즉시 실패하면
    응답 시간으로 계정 존재가 드러난다.

- **결정 (9) 요청에 없었지만 넣은 것과 그 이유**
  | 기능 | 이유 |
  |---|---|
  | 본인 비밀번호 변경 | 초기화 강제 변경이 성립하려면 필수 |
  | 세션 강제 만료 | ADR-015 에 "원격 로그아웃 불가" 로 남아 있던 약점 |
  | 계정 잠금/해제 | 계정별 브루트포스 방어. 잠기면 관리자가 풀어야 한다 |
  | 감사 로그 조회 화면 | 로그를 SQL 로만 볼 수 있으면 실제로 안 본다. 액션 필터 포함 |
  | 마지막 관리자·본인 보호 | 되돌릴 수 없는 실수를 구조적으로 차단 |
  | 비상 복구 계정 유지 | 완전 잠금 방지 |

- **결정 (10) 인증 모듈을 3층으로 나눴다**
  `auth.ts`(암호·토큰·쿠키, DB 모름) / `users.ts`(계정 CRUD·인증) /
  `session.ts`(둘을 합쳐 현재 세션 판정). 토큰 로직에 DB 접근이 섞이면 순환 import 가
  생기고 어느 계층에서 실패했는지 구분이 어려워진다.

- **대안** ① Supabase Auth — ADR-015 에서 기각한 이유(RLS 정책을 열어야 한다)가 그대로
  유효하다. ② 세션 테이블 — epoch 로 같은 효과를 얻으면서 테이블·정리 잡이 없다.
  ③ 역할 3개 이상(관리자/상담자/조회전용) — 지금 필요가 없고, `Permission` 구조라
  나중에 역할만 추가하면 된다.

- **남는 위험**
  1. **MFA 가 없다.** 개인정보 조회 화면을 ID/PW 하나로 지킨다. 계정 분리로 책임 추적은
     생겼지만 인증 강도는 그대로다. 다음 개선 대상.
  2. 비상 복구 계정은 **MFA·잠금·이력이 없는 상시 관리자 경로**다. 배지·감사 로그로
     드러내지만 사용 자체를 막지는 않는다. 비밀번호를 강하게 두고 아는 사람을 최소화해야 한다.
  3. `session_epoch` 검증 때문에 **Supabase 장애 시 DB 계정 로그인·세션이 전부 실패**한다
     (비상 계정만 동작). fail-closed 선택이지만 가용성 비용이 있다.
  4. 계정 삭제 시 감사 로그의 계정명이 고아가 된다. FK 를 걸지 않았기 때문이며 의도적이다.
  5. **비밀번호 재사용·이력 검사가 없다.** 같은 비밀번호로 되돌릴 수 있다.
  6. 초기 비밀번호 전달 경로는 시스템 밖이다(메신저로 보내면 거기 남는다).

- **검증** typecheck·lint·build 통과, 관리자 **9개 라우트 모두 Dynamic**.
  브라우저 **23개 항목 통과** — 신규 라우트 6개 미인증 차단 / **DB 미연결 상태에서
  비상 복구 로그인 성공** / 비상 배지·역할 배지·관리자 내비게이션 / 계정 관리·감사 로그
  화면 진입 / 권한 선택 2개 / 감사 로그 필터 / 비상 계정은 비밀번호 변경 폼 미노출 /
  UUID 아닌 계정 id → 404 / 로그아웃 시 쿠키 제거.
  권한 매트릭스·비밀번호·아이디 규칙은 **로직 단독 실행 19개 항목**으로 확인.
  **DB 가 붙은 계정 흐름(생성·권한 변경·초기화·잠금·세션 만료·상담자 역할 제한)은
  이 환경에서 검증하지 못했다** — 마이그레이션 적용 후 스모크 테스트가 필요하다.

## ADR-020. 첫 로그인은 강제가 아니라 **안내**로 만든다

- **맥락** ADR-019 에서 `must_change_password` 로 초기 비밀번호 사용을 막았지만, 화면에는
  한 줄("비밀번호를 변경해야 다른 화면을 이용할 수 있습니다")뿐이었다. 사용자 요청:
  **"계정 생성 후 최초 로그인 시 해당 계정 사용자가 비밀번호 변경 하도록 안내 하자.
  비밀번호 변경창과 함께"**.

- **결정 (1) 지시가 아니라 이유를 설명한다** — 처음 들어온 담당자는 "왜 바꿔야 하는지"
  와 "바꾸면 무엇을 할 수 있는지" 를 모른다. 한 줄 경고만 두면 **지시로만 읽히고**,
  초기 비밀번호를 그대로 쓰려는 시도(관리자에게 "그냥 쓰면 안 되냐" 문의)가 생긴다.
  세 가지를 명시했다.
  1. 초기 비밀번호는 **전달 경로(메신저·메일)에 그대로 남아 있다** — 그 경로를 볼 수
     있는 사람은 누구나 로그인할 수 있다
  2. 이 화면 안쪽은 **고객의 이름·연락처·문의 내용**을 다루고, 모든 조회·변경이
     담당자 이름으로 기록된다
  3. 바꾸면 **관리자도 그 값을 알 수 없다** — 기록에 남는 행위가 본인의 것임이
     그때부터 성립한다
  - 이어서 **변경 후 쓸 수 있는 권한**(`ROLE_DESCRIPTION`)을 보여준다. 무엇을 얻는지
     모르면 절차가 장애물로만 느껴진다.
  - **"전달받은 초기 비밀번호를 지금 삭제하라"** 를 명시했다. 변경만 하고 메신저에
     남겨두면 위 1번이 그대로 남는다.

- **결정 (2) 강제 변경 중에는 내비게이션을 숨긴다** — 초기 비밀번호 상태에서는 어느
  링크를 눌러도 가드가 되돌려보낸다. 링크를 그대로 두면 **"눌렀는데 아무 일도 안 난다"**
  로 읽혀 담당자를 혼란스럽게 하고, 화면이 고장 난 것으로 오해된다.
  숨긴 대상: 문의·계정·감사 로그 링크, 사용자명 링크(자기 자신), **브랜드 링크**.
  대신 `비밀번호 변경 후 이용 가능` 을 표시한다(좁은 화면에서는 본문과 중복이라 숨김).
  **로그아웃은 남긴다** — 잘못된 계정으로 로그인한 경우 빠져나갈 길이 있어야 한다.
  - 브랜드 링크는 검증에서 놓쳤다가 **링크 `href` 를 세어 보는 테스트로 발견**했다.
    텍스트만 확인하면 이런 종류의 누락을 못 잡는다.

- **결정 (3) 계정을 만든 관리자에게도 안내한다** — 담당자 화면만 고쳐서는 절차가
  완결되지 않는다. 계정 생성 직후(`?created=1`) 상세 화면에 **"담당자에게 전달할 내용"**
  을 띄운다: 로그인 주소·아이디, 안전한 경로로 초기 비밀번호 전달 후 **그 메시지 삭제**,
  첫 로그인에서 변경이 강제된다는 사실.
  - **초기 비밀번호는 다시 확인할 수 없다**(해시만 저장)는 점도 함께 알린다.
    모르면 "어디서 다시 보나" 를 찾다가 시간을 쓴다.

- **대안** ① 로그인 화면에서 안내 — 아직 누구인지 모르므로 개인화할 수 없고,
  변경 화면과 떨어져 있어 맥락이 끊긴다. ② 이메일 발송 — 발송 인프라가 없고,
  초기 비밀번호를 메일에 담는 것은 위 1번을 악화시킨다.

- **남는 위험** 안내가 길어 **읽지 않고 넘길 수 있다.** 그래도 강제 변경 자체는
  코드로 막혀 있으므로 보안 효과는 유지된다. 안내는 이해를 돕는 장치다.
  초기 비밀번호 전달 경로는 여전히 시스템 밖이다(ADR-019 의 남는 위험).

- **검증** 임시로 세션을 `mustChangePassword: true` 로 만들어 **DB 계정 첫 로그인과
  동일하게 렌더**한 뒤 라이트·다크·모바일 스크린샷 확인, 10개 항목 통과 —
  되돌려보내는 링크 4종(`/admin`·`/admin/users`·`/admin/audit`·`/admin/password`)
  **모두 부재**, 로그아웃 유지, 폼 3필드 + 버튼 존재, 390px 가로 스크롤 없음.
  강제 변경 중 `/admin`·`/admin/users` 접근이 비밀번호 화면으로 리다이렉트되고
  **비밀번호 화면 자체는 루프가 없음**도 확인. 임시 패치는 원복해 커밋에 포함하지 않았다
  (`git diff --exit-code` 로 확인).

## ADR-021. 보관기간 파기를 DB 함수 + pg_cron 으로, 방침의 예외 조항까지 구현한다

- **맥락** 개인정보처리방침 4항에 **"수집일로부터 3년간 보유한 후 지체 없이 파기"**
  라고 적어 두고 삭제 수단이 없었다. **적어 두고 하지 않는 것이 위반**이다.
  문의 폼을 내려둔 동안에는 데이터가 쌓이지 않아 미뤄왔지만, 관리자 직접 등록
  (ADR-018)으로 개인정보가 다시 쌓이기 시작해 더 미룰 수 없었다.

- **결정 (1) 방침의 예외 조항을 함께 구현한다** — 방침에는 4항에 이런 문장이 있다.
  > "단, 계약이 체결된 경우 관련 법령이 정한 기간(예: 전자상거래법상 계약 및
  >  청약철회 기록 5년) 동안 보관합니다."

  **일괄 3년 삭제만 만들면 이 조항을 지킬 수 없다.** `inquiries` 에
  `retain_until date` / `retain_reason text` 를 두어 개별 보존 기한을 설정할 수 있게
  했다. 파기 함수는 `retain_until` 이 미래인 행을 건너뛴다.
  - `retain_until` 한 컬럼으로 "계약 체결 5년" 뿐 아니라 분쟁·조사 등 다른 보류도
    표현된다. 사유별 boolean 을 여러 개 두는 것보다 낫다고 판단했다.
  - **남는 위험: 설정은 수동이다.** 계약이 체결됐는데 아무도 설정하지 않으면 3년에
    파기된다. **코드로 강제할 수 없다** — 계약 체결 사실이 이 시스템에 없기 때문이다.
    운영 절차로 정해야 한다.

- **결정 (2) 보관기간을 함수 인자로 받지 않고 상수로 박는다** —
  `purge_expired_inquiries(p_triggered_by text)` 는 기간을 받지 않는다.
  인자로 열어 두면 누군가 `interval '1 day'` 로 호출해 **전체를 지울 수 있다.**
  기간을 바꾸려면 마이그레이션으로 함수를 교체해야 하고, 그 변경이 PR 로
  검토·기록된다. **처리방침에 적힌 기간과 코드가 갈리지 않게 하는 장치**다.

- **결정 (3) 파기 이력을 남긴다** — `data_retention_log`.
  "지체 없이 파기했다" 는 주장은 **증빙이 있어야 성립한다.** 전자금융 도메인에서
  삭제 사실을 입증할 수 없으면 하지 않은 것과 같다.
  - **삭제된 개인정보는 남기지 않는다.** 건수·기준일·트리거(cron/manual)만 기록한다.
    파기 이력에 개인정보를 남기면 파기의 의미가 사라진다.
  - **삭제 대상이 0건이어도 행을 남긴다.** 그 0 행이 **"잡이 돌고 있다" 는 유일한
    증거**다. 행이 없으면 잡이 죽은 것이다. 이 판단이 결정 (5)로 이어진다.

- **결정 (4) 감사 로그는 5년, 문의는 3년** — `admin_audit_log` 는 개인정보를 담지
  않는다(`ip_hash` 만). 사고 조사 목적이므로 더 오래 보관하는 편이 낫다.
  `inquiry_status_history` 는 `on delete cascade` 로 문의와 함께 사라진다(ADR-018).

- **결정 (5) 마이그레이션을 두 파일로 나눈다** —
  `20260910000006_data_retention.sql`(함수·이력·컬럼) /
  `20260910000007_schedule_retention_job.sql`(pg_cron 스케줄).
  **`create extension pg_cron` 은 플랜·권한에 따라 거부될 수 있고, 그러면 트랜잭션
  전체가 롤백된다.** 함수까지 함께 날아가면 수동 실행조차 못 하게 된다.
  나눠 두면 함수만 적용하고 스케줄은 나중에 붙일 수 있다.
  - 잡은 **UTC 기준** cron 이다(`10 18 * * *` = 03:10 KST). 두 잡을 20분 벌려 둬
    잠금·부하가 겹치지 않게, 그리고 실패 시 어느 잡인지 구분되게 했다.

- **대안** ① 애플리케이션 레벨 배치(Vercel Cron + 라우트) — 외부에서 호출 가능한
  엔드포인트가 늘어난다. 시크릿 헤더로 막아도 공격면이 생기고, DB 안에서 끝나는
  일을 굳이 밖으로 낼 이유가 없다. **pg_cron 을 못 쓰는 플랜이면 이 방법으로
  전환한다**(그때는 라우트 인증 설계를 먼저 문서화한다).
  ② Supabase Edge Function + 스케줄 — 같은 이유로 뒤로 뒀다.
  ③ `retain_until` 없이 일괄 3년 — 방침의 예외 조항과 충돌한다.

- **남는 위험**
  1. **잡이 등록됐다고 도는 것은 아니다.** `data_retention_log` 에
     `triggered_by = 'cron'` 행이 매일 쌓이는지 확인해야 한다. 이 확인을
     `content/features.ts` 의 폼 재활성화 전제조건과 `doc/10-admin.md` 에 넣었다.
  2. `retain_until` 수동 설정 (결정 1).
  3. **마케팅 수신 동의 철회 수단이 없다.** 방침은 "동의 철회 시 즉시 파기" 라고
     적었지만 철회를 받는 창구·기능이 없다. 수동 처리 절차도 미문서화다.
  4. pg_cron 사용 가능 여부를 **아직 확인하지 못했다.**

- **검증** 함수·스케줄 SQL 을 작성했고 `typecheck`·`lint`·`build` 통과.
  **DB 에 적용해 실제로 파기가 일어나는지는 검증하지 못했다** — 이 환경에 Supabase
  접근이 없다. 적용 후 사용자 환경에서 사전 점검 쿼리(파기 대상 건수 미리 보기)와
  `select * from public.purge_expired_inquiries('manual')` 로 확인이 필요하다.

## ADR-022. "배포 실패" 가 아니라 **배포가 생성되지 않은 것**이었다 — 그리고 그 규칙에 해제 조건을 붙인다

- **증상** PR #10 이 CI 통과·`main` 머지까지 끝났는데 **프로덕션이 옛 내용을 계속
  서빙**했다. Vercel Deployments 에는 세 건이 있었지만 **전부 `Preview`** 였고
  브랜치는 모두 작업 브랜치였다. `Production` 항목이 **아예 없었다.**

- **원인** 머지 후 작업 브랜치를 `main` 의 HEAD 로 force-push 한 것. **Vercel 은
  같은 커밋을 두 번 빌드하지 않는다.** 브랜치 push 가 먼저 도착하면 그 SHA 가
  **Preview 로 선점**되고, 이후 `main` 이 같은 SHA 를 가리켜도 **Production 배포가
  만들어지지 않는다.** 배포가 실패한 것이 아니라 **존재하지 않았다.**

- **왜 두 번이나 놓쳤나** 이 세션에서 **초록 신호를 배포 성공으로 읽은 것이 두
  번**이다(다른 프로젝트의 200 응답, 그리고 CI 통과). **CI 통과·200 응답·머지 완료는
  모두 "프로덕션에 반영됐다" 를 뜻하지 않는다.** 확인해야 하는 것은
  **`Production` 환경의 배포가 그 SHA 로 존재하는가** 하나다.

- **결정 (1) 머지 직후 작업 브랜치를 push 하지 않는다.** 로컬에서만 `origin/main`
  기준으로 다시 만든다.

- **결정 (2) 단, 금지 규칙에 해제 조건을 명시한다.** 처음에는 "push 하지 않는다" 로만
  적었는데, **해제 조건이 없는 금지는 stop hook(미푸시 커밋 경고)과 매번 교착된다.**
  실제로 이 교착이 발생했다. 금지되는 것은 좁게 하나다 — **Production 배포가 생기기
  전에 같은 SHA 를 Preview 로 선점하는 것.** 따라서 다음 중 하나면 push 해도 된다.
  1. 머지 커밋의 **Production 배포가 이미 생성**되었다
  2. push 할 커밋이 **머지 커밋과 다른 SHA** 다 (= 새 커밋이 생겼다)

  확인은 GitHub Deployments API 로 한다(Vercel 토큰이 필요 없다):

  ```sh
  curl -sS "https://api.github.com/repos/NextChans/homepage_-template/deployments?sha=<merge-sha>" \
    -H "Accept: application/vnd.github+json"
  ```

  `environment` 가 `Production` 인 항목이 있으면 위험은 지나갔다. 이 명령을
  `CLAUDE.md` 규칙 6에 넣었다.

- **결정 (3) stop hook 경고를 근거로 push 하지 않는다.** hook 은 브랜치 tip 만
  비교하므로 **"이미 `origin/main` 에 있는 커밋"** 과 **"유실 위험이 있는 커밋"** 을
  구분하지 못한다. `git log origin/main..HEAD` 가 비어 있으면 유실될 것이 없고,
  그 경고는 **오탐**이다. 훅을 신뢰해 push 하면 결정 (1)이 막으려던 사고가 그대로
  재발한다.

- **대안** 작업 브랜치를 리셋하지 않고 계속 쓴다 — 이미 머지된 PR 에 커밋이 쌓이고,
  base 가 낡아 다음 PR 의 diff 가 부풀어 채택하지 않았다.

- **남는 위험** 이 프로젝트의 배포는 **Vercel 대시보드 설정에 의존**한다. Production
  브랜치가 `main` 이 아니게 바뀌면 위 확인 절차가 통째로 무의미해진다. 배포가
  이상하면 **먼저 Production 브랜치 설정을 본다.**

- **검증** PR #12(`f7c4d43`)·PR #13(`141d567`) 머지 후 GitHub Deployments 를 조회해
  **두 머지 커밋 모두 `environment=Production` 배포가 생성된 것을 확인**했다.
  작업 브랜치 커밋(`e82ac34`)은 `Preview` 로 따로 잡혀 SHA 충돌이 없었다.
  프로덕션 응답도 `<title>WITUS — …` 로 실제 변경을 반영했다.

## ADR-023. 로고를 사이트에 맞춘다 — 심볼은 `currentColor`, 골드는 래스터 자산에만

- **맥락** 사명 확정(WITUS) 후 로고안 6개를 받았다. 아이덴티티 팔레트는 Deep
  Navy `#0A1F44` + Gold `#C9A961` 인데, 사이트는 **화이트 + `accent` 단색**
  체계다(Apple 스타일). 두 체계를 그냥 합치면 **한 화면에 두 브랜드**가 생긴다.

- **결정 (1) 안 1 "Shield of Trust" 를 채택했다.** 신뢰·보안이 이 사업의 핵심
  가치와 맞고, 결제 도메인에서 방패는 PCI DSS·보안 인증 문맥의 관용구다.

  **채택하지 않은 안 중 두 개는 취향이 아니라 리스크 때문이다** —
  - 안 3 *상승 화살표*: 증권·투자자문으로 읽히고, 더 중요하게는 **전자금융업 등록
    컨설팅 회사가 상승 그래프를 쓰면 "승인·수익 보장" 으로 읽힐 수 있다.**
    `CLAUDE.md` 가 `100% 승인`·`반드시 통과` 문안을 금지한 것과 같은 이유다.
    **문안으로 못 하는 주장을 로고로 하면 안 된다.**
  - 안 5 *다이아몬드*: 보석·럭셔리 기호로, 결제 인프라와 의미 연결이 없다.

- **결정 (2) 사선을 3개에서 2개로 줄였다.** 파비콘 16px 에서 사선 3개는 선과 간격이
  각각 1px 미만이 되어 **한 덩어리로 뭉갠다.** 2개로 줄이고 굵혀 실제 16px 렌더로
  판독을 확인했다.

- **결정 (3) 팔레트는 (A)안 — 로고를 사이트에 맞춘다.**
  - 화면(헤더·푸터)의 심볼은 **`currentColor`** 로 그린다. 라이트에서 잉크색,
    다크에서 흰색으로 자동 반전된다(측정: `rgb(29,29,31)` / `rgb(245,245,247)`).
  - **골드·네이비는 래스터 아이덴티티 자산에만** 쓴다: 파비콘, 앱 아이콘, OG 이미지.
  - **골드를 텍스트·링크·버튼에 쓰지 않는다.** 흰 배경 대비비가 **2.25:1** 로
    WCAG AA(본문 4.5:1, UI 3:1)에 미달한다. 네이비는 16.2:1 로 문제없지만
    사이트 강조색은 `accent` 하나로 유지한다.
  - 대안 (B) 사이트를 로고에 맞춤(네이비 기반 리디자인)은 채택하지 않았다 —
    골드가 여전히 텍스트로 못 쓰이므로 강조색이 따로 필요해지고, 사실상 전면
    리디자인이다.

- **결정 (4) 도형은 `content/brand.ts` 한 곳에만 둔다.** 컴포넌트와 자산 생성
  스크립트가 같은 값을 읽는다. 복사해 두면 심볼을 다듬을 때 **화면과 파비콘이 갈린다.**
  - **`fill-rule="evenodd"` 로 그린다.** 사선이 서브패스로 들어 있고 evenodd 가
    그것을 구멍으로 만든다. `<mask>` 를 쓰면 `id` 가 필요하고 헤더·푸터에서 두 번
    렌더될 때 **중복 id** 가 된다 — `useId()` 로 풀려면 클라이언트 컴포넌트가 되어야
    하는데 심볼 하나 때문에 그럴 이유가 없다.
  - ⚠️ evenodd 는 도형 밖으로 나간 부분을 잘라주지 않고 **거기까지 칠한다.**
    사선 좌표는 방패 내부에 완전히 들어가도록(여백 최소 2.4) 계산되어 있다.

- **결정 (5) 파비콘·OG 를 런타임(`ImageResponse`) 대신 미리 생성해 커밋한다.**
  런타임 생성은 **폰트 의존이 배포 후로 넘어가고**, OG 이미지는 깨져도 화면상 증상이
  없어 **깨진 걸 모른 채 지나간다.** 스크립트(`scripts/generate-brand-assets.mjs`)로
  만들고 결과물을 눈으로 확인해 저장소에 고정했다.
  - 파비콘은 **네이비 배경 + 골드 심볼**이다. 투명 배경으로 두면 **다크 모드 탭에서
    안 보인다.**
  - 앱 아이콘은 정사각 풀블리드다 — **iOS 가 자체 라운드를 적용**하므로 여기서 깎으면
    모서리가 이중으로 깎인다.
  - **OG 이미지에 워드마크 텍스트를 넣지 않았다.** 이 환경에는 DejaVu Sans 밖에 없어
    (브랜드 서체 Inter/Manrope 없음) 잘못된 서체가 PNG 에 **영구히 굽힌다.** 사명은
    OG 카드의 제목 텍스트로 이미 노출된다. 넣으려면 **폰트 파일을 커밋**해야 한다
    (웹·임베딩 라이선스 확인 선행).

- **남는 위험**
  1. **`WORK IN TRUST US` 는 영어로 비문이다.** `Work in trust us` 는 문장이 되지
     않는다. 사용자가 이 표기를 유지하기로 결정했다(2026-09-10). 임의로
     `WORK IN TRUST` 로 줄이지 않는다.
  2. **선행 상표를 확인하지 않았다.** 방패+사선은 선행 상표가 많을 가능성이 높다.
     키프리스 유사군 검색이 필요하고, 출원은 그라데이션이 아닌 **단색 도형**으로 하는
     것이 일반적이다.
  3. 단말기 실크스크린·계약서 등 **1도 인쇄용 버전**은 아직 만들지 않았다.
     심볼이 `currentColor` 단색 도형이라 변환은 쉽다.

## ADR-024. Vercel Web Analytics — 대시보드 토글만으로는 아무것도 수집되지 않는다

- **맥락** 사용자가 Vercel 대시보드에서 Web Analytics 를 켰다. 그런데 **토글만으로는
  수집이 시작되지 않는다** — 페이지에 `<Analytics />` 컴포넌트가 있어야 스크립트가
  주입된다. 대시보드에서 "켰다" 고 믿는 상태로 데이터가 0 인 채 지나갈 수 있다.

- **결정 (1) `features.analytics` 플래그로 컴포넌트를 켠다.** 기존 플래그 구조를
  따른다 — 켜고 끄는 판단이 **컴플라이언스 결정**이므로 대시보드에서 조용히 바뀌면
  안 되고 PR 로 검토·기록되어야 한다(`content/features.ts` 서두 참고).

- **결정 (2) `app/privacy/page.tsx` 를 함께 고쳤다.** `CLAUDE.md` 의 강제 규칙이다
  (개인정보 수집 항목을 늘리면 처리방침을 반드시 함께 갱신).
  - 1항: 방문 분석 자동 수집 항목(페이지 경로·리퍼러·국가 수준 위치·기기/브라우저).
    **쿠키 미사용·방문자 식별자 미생성**을 명시했다.
  - 2항: 이용 목적에 통계 분석 추가. 3항: 집계 형태 보관 명시.
  - 4항: 수탁자에 **Vercel Inc.** 추가, 호스팅·통계 처리의 국외 인프라 가능성 명시.

- **⚠️ 남는 위험 — 지금 상태는 수집은 하는데 처리방침을 볼 수 없다.**
  `features.privacyPolicy` 가 `false` 라 `/privacy` 가 **404** 다. 개인정보보호법
  제30조(처리방침 수립·**공개**) 관점에서 문제가 된다.
  - 해소에 필요한 것: **실제 사업자등록번호와 개인정보 보호책임자** 값
    (현재 `content/site.ts` 의 TODO — 각각 `000-00-00000`, `김철수`).
  - **플레이스홀더 상태로 `privacyPolicy` 를 켜지 않았다.** 허위 사업자 표시 정보를
    게재하는 것이 404 보다 나쁘다.
  - 값이 채워지면 `privacyPolicy` 를 켠다. **그때까지는 `analytics` 를 끄는 것이
    안전한 선택**이며, 켜 둔 것은 사용자 판단이다(2026-09-10).

- **대안** Vercel 이 만든 PR #2 를 머지 — base 가 `main` 이 아니라 **이미 사라진
  작업 브랜치 커밋**(`3eab96c`)이라 그대로는 머지할 수 없었다. 같은 변경을 직접
  구현했으므로 PR #2 는 불필요해졌다.

- **검증** `typecheck`·`lint`·`build` 통과. 로컬 프로덕션 서버에서 클라이언트 번들에
  `_vercel/insights` 참조가 포함된 것을 확인했다. ⚠️ **서버 HTML 에는 스크립트 태그가
  없다** — `<Analytics />` 는 클라이언트에서 주입하므로 정상이다. 실제 수집 여부는
  **Vercel 대시보드에 데이터가 들어오는지**로만 확인할 수 있다.

## ADR-025. 정규 도메인은 apex `witus.kr` — canonical 을 넣고 도메인은 코드에 박는다

- **맥락** `witus.kr` 도메인을 구입했다. Vercel 에 붙이면 **`*.vercel.app` 주소는
  사라지지 않는다** — Vercel 이 자동 배정하는 주소는 제거할 수 없다. 같은 내용이
  두 호스트로 응답하는 상태가 영구적으로 남는다.

> **정정 (2026-09-10)**: 위 맥락 중 "두 호스트가 응답하는 상태가 영구적으로 남는다" 는
> **부정확했다.** `*.vercel.app` 은 **목록에서 삭제할 수는 없지만 리다이렉트는 된다** —
> Domains 목록의 해당 행에 **Redirect to Another Domain** 이 있다. 실제 대시보드 화면을
> 보고 확인했다.
> → 최종 구성은 **`witus.kr` 만 콘텐츠를 내려주고 `www` 와 `*.vercel.app` 은 리다이렉트**다.
> `canonical` 은 그래도 유지한다: (a) 리다이렉트를 걸기 전까지의 기간을 덮고,
> (b) Vercel 이 `307 Temporary` 만 제공하면 색인 통합 신호가 약해 canonical 이 필요하다.
> ⚠️ **순서가 중요하다** — `witus.kr` 이 열리는 것을 확인하기 **전에** `*.vercel.app` 에
> 리다이렉트를 걸면 **살아 있는 주소가 하나도 없게 된다.** 절차는
> `doc/09-deployment.md` 3-4절 1)에 순서대로 적었다.

- **결정 (1) apex(`witus.kr`)를 정규로 삼고 `www` 는 리다이렉트한다.**
  - 짧고, 구입한 것이 apex 다. 국내 B2B 사이트에서 `www` 를 붙일 이유가 약하다.
  - ⚠️ **apex 는 CNAME 을 쓸 수 없다**(RFC 제약) → **A 레코드**가 된다. Vercel 이 IP 를
    바꾸면 수동으로 따라가야 한다. 등록업체가 ALIAS/ANAME 을 지원하면 그게 낫다.
    → **확인 결과 이 도메인의 등록업체(가비아)는 ALIAS/ANAME 을 제공하지 않는다.**
    A 레코드 고정이고, IP 변경 시 수동 대응이 필요하다. 이 비용을 알고 택했다.
  - 대안 `www` 정규: CNAME 을 쓸 수 있어 IP 변경에 자유롭다. 채택하지 않았다 —
    주소가 길어지는 대가가 이 규모에서 더 크다.

- **결정 (2) `alternates: { canonical: './' }` 를 루트 레이아웃에 넣었다.**
  두 호스트가 응답하는 것을 막을 수 없으므로 **색인을 통합**한다.
  - ⚠️ **`'./'` 상대 경로여야 한다.** `metadataBase` 기준으로 **현재 경로**로 해석되어
    `/services/kiosk` → `https://witus.kr/services/kiosk` 가 된다.
    **절대 URL 을 박으면 모든 페이지가 홈을 가리켜 하위 페이지가 색인에서 사라진다.**
    경로별로 다르게 나오는지 실제로 확인했다.
  - canonical 은 색인만 통합한다. **주소 자체는 계속 살아 있다** — 대외 문서에는
    `witus.kr` 만 쓴다.

- **결정 (3) 도메인을 `lib/site-url.ts` 의 기본값으로 코드에 박았다.**
  도메인은 환경별 비밀값이 아니라 **프로젝트의 사실**이다. 대시보드에만 있으면
  로컬·프리뷰가 다른 주소를 내보내고 설정 누락을 아무도 못 본다. 코드에 두면 PR 로
  검토되고 모든 환경에서 같다 — `content/features.ts` 가 플래그를 코드에 두는 것과
  같은 이유다.
  - ~~**우선순위는 그대로 뒀다**: `NEXT_PUBLIC_SITE_URL` →
    `VERCEL_PROJECT_PRODUCTION_URL` → 기본값. 2번이 **도메인 전환을 자동으로
    처리**한다.~~

    > **정정 (2026-09-10, 실측)**: **이 가정은 틀렸다.** `VERCEL_PROJECT_PRODUCTION_URL`
    > 은 커스텀 도메인을 따라오지 **않았다.** `witus.kr` 을 Production 에 연결하고
    > 인증서 발급까지 끝나 `https://witus.kr` 이 정상 서빙되는 상태에서 **새
    > Production 배포를 만들어 확인했는데도** 계속
    > `homepage-template-ivory.vercel.app` 을 반환했다.
    >
    > 결과적으로 canonical·sitemap·og:image 가 **커스텀 도메인이 아니라 vercel.app 을
    > 가리켰다** — canonical 로 막으려던 중복 색인 문제를 canonical 자신이 만드는
    > 상태였다. 화면에는 아무 증상이 없어 **모르고 지나갈 수 있었다.**
    >
    > → **체인에서 제거했다.** 이제 `NEXT_PUBLIC_SITE_URL` → `DEFAULT_SITE_URL` 뿐이다.
    > 도메인은 코드가 아는 사실이고, Vercel 이 어떤 별칭을 프로덕션으로 보는지는
    > 우리가 통제할 수 없다. **되살리지 말 것.**
    >
    > 회귀 검증: `VERCEL_PROJECT_PRODUCTION_URL=homepage-template-ivory.vercel.app` 을
    > 주고 빌드해도 canonical 이 `https://witus.kr/services` 로 나오는 것을 확인했다.
    >
    > ⚠️ 또한 **canonical·sitemap 은 빌드 시점에 구워진다.** 도메인 관련 변경은
    > **재배포해야** 반영된다 — 대시보드만 만져서는 바뀌지 않는다.
  - `isPlaceholderSiteUrl` 을 제거했다. 기본값이 실도메인이 된 뒤로는 **항상 `false`**
    인 상수여서 이름이 거짓말을 한다. 쓰이는 곳도 없었다.

- **⚠️ 남는 위험 — HSTS preload 는 되돌리기 어렵다**
  `next.config.ts` 가 `max-age=63072000; includeSubDomains; preload` 를 보낸다.
  - **헤더만으로는 preload 목록에 등록되지 않는다** — hstspreload.org 에 직접 제출해야
    한다. **서브도메인 계획이 확정되기 전에는 제출하지 않는다.** 제거에 몇 달이 걸린다.
  - 다만 **`includeSubDomains` 는 지금도 효력이 있다.** 브라우저가 apex 를 한 번
    방문하면 모든 서브도메인에 HTTPS 를 강제한다. HTTP 만 제공하는 서브도메인
    (구형 메일·그룹웨어 등)을 붙일 계획이면 먼저 확인해야 한다.

- **남는 위험 2** 도메인이 바뀌면 **관리자 세션이 끊긴다**(쿠키는 호스트에 묶인다).
  다시 로그인하면 되고 데이터 영향은 없다.

- **검증** 로컬 프로덕션 빌드에서 `canonical` 이 경로별로 정확히 해석되는 것
  (`/`, `/services`, `/about`, `/services/kiosk`), `sitemap.xml`·`robots.txt`·`og:image`
  가 모두 `witus.kr` 인 것을 확인했다.
  ⚠️ **실제 도메인 연결과 DNS 는 검증하지 못했다** — 대시보드·등록업체 작업이고 이
  환경에서 할 수 없다. 절차와 확인 명령은 `doc/09-deployment.md` 3-4절에 있다.
