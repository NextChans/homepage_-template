# 06. 보안 · 개인정보 · 표시광고

전자금융 업종 사이트라 마케팅 페이지라도 리스크가 일반 기업 홈페이지보다 크다.
**해결한 것과 남은 것을 분리해 기록한다. 남은 항목은 지우지 않는다.**

## 적용한 조치

### 애플리케이션

| 항목 | 구현 |
|---|---|
| 보안 헤더 | `next.config.ts` — `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, HSTS(preload) |
| 서버 정보 은닉 | `poweredByHeader: false` |
| 서버 전용 모듈 격리 | `lib/supabase/server.ts` 에 `import 'server-only'` |
| 비밀키 노출 방지 | `SUPABASE_SERVICE_ROLE_KEY` / `INQUIRY_IP_HASH_SALT` 에 `NEXT_PUBLIC_` 미사용 |
| 입력 검증 | `lib/inquiry-schema.ts` (zod) — 서버에서 재검증. 클라이언트 검증만 신뢰하지 않는다 |
| 봇 차단 | honeypot(`company_website`) + 최소 작성시간 2초 |
| 어뷰징 억제 | `ip_hash` 기준 10분 3건 레이트리밋 |
| 로그 위생 | 에러 로그에 입력값(개인정보) 미출력. `error.code`/`message` 만 |

### 데이터

| 항목 | 구현 |
|---|---|
| 접근 통제 | `inquiries` RLS on + 정책 없음 + `revoke all from anon, authenticated` |
| 수집 최소화 | 이름·회사·이메일·연락처·문의내용만. 고유식별정보·금융정보 미수집 |
| IP 비식별화 | salt + SHA-256 해시만 저장. salt 없으면 미저장 |
| 동의 증빙 | `privacy_consent` (필수, `check` 제약으로 false 저장 차단), `marketing_consent` (선택) 분리 저장 |
| 감사 필드 | `created_at`, `updated_at`(트리거), `status`, `handled_at`, `handled_by` |
| 민감정보 입력 억제 | 폼에 "주민등록번호·계좌·카드번호 입력 금지" 안내 문구 |

### 접근성

skip link, `aria-invalid` / `aria-describedby` 로 필드 에러 연결, `aria-expanded`/`aria-controls`
모바일 메뉴, 포커스 링 유지, `prefers-reduced-motion` 대응, `<noscript>` 리빌 폴백.

## 현재 비활성 상태인 기능 (2026-09-10)

`content/features.ts` 의 플래그로 내려둔 것. **재활성화 시 체크리스트는 그 파일의 주석**에 있다.

| 기능 | 상태 | 이유 |
|---|---|---|
| 상담 문의 폼 (`/contact` 입력 폼 + Supabase 저장) | **꺼짐** | 개인정보를 수집하지 않고 전화·이메일로만 문의를 받는다 |
| 개인정보처리방침 (`/privacy`) | **꺼짐 (404)** | 초안 상태. 확정된 내용이 없다. 소스는 보존 |
| 접수 Slack 알림 | 배선만 | `SLACK_INQUIRY_WEBHOOK_URL` 미설정. 폼을 켤 때 함께 활성화 |
| Vercel Web Analytics | **켜짐** | 사용자 판단으로 활성화(2026-09-10). ⚠️ 아래 근거를 깨뜨린다 |

**이 조합이 성립하는 근거**: 폼을 내려 **개인정보를 수집하지 않으므로** 처리방침 비공개와
보관기간 삭제 잡 부재가 당장의 위반을 만들지 않는다. 서버 측에서도 `submitInquiry` 가
플래그를 검사해 차단하므로 UI 우회 POST 로도 저장되지 않는다 (ADR-014).

> ⚠️ **`features.inquiryForm` 을 켜는 순간 위 근거가 사라진다.** 켜기 전에 반드시:
> 처리방침 확정 및 공개(`privacyPolicy` 동시 활성) · 보관기간 삭제 잡 구성 · 접수 알림 활성화.
> 플래그 주석에 같은 내용을 적어두었지만 **코드로 강제하지는 않는다.**

> ⚠️ **그런데 `features.analytics` 가 이미 그 근거를 깨뜨렸다** (2026-09-10, ADR-024).
> 문의 폼은 여전히 꺼져 있지만 **방문 분석이 자동 수집을 시작**했다(페이지 경로·리퍼러·
> 국가 수준 위치·기기/브라우저. 쿠키·방문자 식별자는 없다). 즉 **"개인정보를 수집하지
> 않는다" 는 전제가 더는 성립하지 않는데 처리방침은 404 다.**
> 개인정보보호법 제30조는 처리방침의 수립뿐 아니라 **공개**를 요구한다.
>
> 처리방침 본문은 이미 갱신해 두었다(1·2·3·4항). **막힌 것은 문안이 아니라 값이다** —
> 실제 **사업자등록번호**와 **개인정보 보호책임자**가 필요하다. 플레이스홀더
> (`000-00-00000`, `김철수`)로 공개하는 것은 **허위 사업자 표시 정보**여서 404 보다 나쁘다.
> 값이 확보되면 `privacyPolicy` 를 켠다. 그때까지는 `analytics` 를 끄는 것이 안전하다.

## 남은 리스크 (운영 전 처리)

### 높음

- [ ] **`service_role` 키 관리** — 유출 시 DB 전체 노출. 배포 플랫폼 시크릿 저장소 사용,
      로테이션 주기 정의, 접근 권한자 명단 관리가 필요하다.
- [ ] **개인정보처리방침이 초안**이다 — 수집 항목·보유기간(3년)·수탁자를 실제 운영과
      일치시키고 법무/준법감시 검토를 받아야 한다.
      **현재 페이지는 비공개(404)로 내려두었다** (`features.privacyPolicy = false`).
      폼도 함께 내려 개인정보를 수집하지 않는 동안에만 성립하는 상태다.
      - 보관 리전은 **서울(`ap-northeast-2`)** 로 확정해 4항에 반영했다.
      - **남은 판단: 국외 이전 해당 여부.** 저장 리전이 국내여도 수탁자(Supabase Inc.)는 국외
        법인이며, Supabase 공식 문서가 **백업·로그·외부 반출·Edge Function 실행·재위탁 업체가
        국외이전 판단에 영향을 줄 수 있다**고 명시한다. 따라서 "국외 이전 없음" 으로 단정하지
        않고 "검토 진행 중" 으로 표기했다. 법무 확정 후 문구를 교체할 것.
      - 확인할 것: Supabase 재위탁 업체(sub-processor) 목록, 백업·로그 보관 위치,
        기술지원 시 국외에서의 데이터 접근 가능 여부.
- [ ] **보관기간 경과 데이터 삭제가 미구현** — 방침에 3년으로 적어두고 삭제 잡이 없으면
      그 자체가 위반이다. `pg_cron` 등으로 구성해야 한다.
      **현재는 폼을 내려 신규 수집이 없으므로 급하지 않다.** 폼 재활성화 전 필수.
- [x] **실적 수치** — 근거 자료가 없어 `XXX+`, `X,XXX대`, `OO`, `OOOO` 플레이스홀더로
      치환 완료 (2026-09-10, ADR-014). 회사 연혁 연도도 함께 치환했다.
      근거를 확보한 항목만 실제 숫자로 바꾸고, **확보하지 못한 항목은 숫자를 만들지 말고
      제거**할 것. 대상: `content/site.ts` 의 `metrics`, `app/page.tsx` 의 `PanelStats`,
      `app/about/page.tsx` 의 `history`.

### 중간

- [ ] **CSP 미설정** — 현재 헤더에 `Content-Security-Policy` 가 없다. 서드파티 스크립트를
      붙이기 전에 nonce 기반 CSP 를 도입한다.
- [ ] **`x-forwarded-for` 신뢰** — 신뢰 프록시 앞단이 없으면 위조 가능. IP 해시를
      인증·권한 판단에 쓰지 않는다는 전제를 유지해야 한다.
- [ ] **레이트리밋이 비원자적** — 동시 요청에서 한도 초과 가능. 어뷰징 억제 목적이라 허용했다.
- [ ] **접수 알림** — Slack 배선은 완료(`lib/notify/slack.ts`), 웹훅 URL 미설정으로 비활성.
      폼을 내린 상태라 지금은 문제되지 않는다. 폼 재활성화 전 필수.
      **알림에 개인정보를 넣지 않는 설계**를 유지할 것 — Slack 은 제3자이고 메시지가
      장기 보존된다. 이름·이메일·연락처·본문을 넣으면 처리방침 수탁자에 Slack 을
      추가해야 한다.
- [x] ~~**관리자 조회 경로 없음**~~ — `/admin` 신설 (2026-09-10). 인증 + 감사 로그
      (`admin_audit_log`) 를 함께 설계했다. 운영 절차는 `doc/10-admin.md`, 근거는 ADR-015.
      **남는 위험은 아래 '관리자 페이지' 절로 이관.**
- [ ] **제휴사 로고/상호** — 서면 사용 동의 전 게재 금지.

### 낮음

- [ ] CSRF 는 Next.js Server Action 의 Origin 검증에 의존. 별도 토큰 없음.
- [ ] 백업/복구 정책(Supabase PITR) 미정.
- [x] CI 추가 (`.github/workflows/ci.yml`) — PR·main push 마다 typecheck / lint / build.
      비밀값을 요구하지 않는다(빌드는 Supabase env 없이 통과하도록 설계).
- [ ] `npm audit` 을 CI 게이트로 넣을지 결정. 현재는 수동 실행.

### 의존성 취약점 현황 (2026-09-10)

| 패키지 | 등급 | 내용 | 처리 |
|---|---|---|---|
| `next` 15.5.4 | — | CVE-2025-66478 (npm 이 deprecated 경고로 표시) | **15.5.25 로 업그레이드 완료** |
| `sharp` | high | libvips/libheif 취약점 (CVE-2026-33327 등) | `npm audit fix` 로 해소 완료 |
| `postcss` | **high** | `</style>` 미이스케이프 XSS, sourceMappingURL 통한 임의 파일 읽기 | **미해소.** next 의 전이 의존이며 수정에 `next@16` (semver major) 필요 |
| `next` | moderate | 위 postcss 전이 | 동일 |

**postcss 는 빌드 타임 도구**라 런타임 노출면은 아니지만, 신뢰할 수 없는 CSS 를 빌드에 넣지
않는다는 전제가 유지되어야 한다. 해소하려면 Next 16 메이저 업그레이드가 필요하므로 별도
작업으로 분리한다 (App Router 호환성·Tailwind v4 연동 재검증 필요).

## 관리자 페이지 (`/admin`) 리스크

**2026-09-10 부터 운영 중이다.** 즉 아래 항목은 가상의 리스크가 아니라
**지금 실제로 고객 개인정보를 지키고 있는 조건**이다.
전체 설계 근거는 ADR-015, 운영 절차는 `doc/10-admin.md`.

### 높음

- [x] ~~**3년 보관기간 삭제 잡 없음**~~ — 구현 완료 (2026-09-10, ADR-021).
      `purge_expired_inquiries()` + `pg_cron` 일 1회. 처리방침의 예외 조항
      (계약 체결 시 법령상 기간 보관)도 `retain_until` 로 구현했다.
      파기 이력은 `data_retention_log` 에 남는다.
      **⚠️ 잡이 등록됐다고 도는 것은 아니다** — `data_retention_log` 에
      `triggered_by = 'cron'` 행이 매일 쌓이는지 확인해야 한다.
- [ ] **개인정보처리방침 미확정·비공개** — 공개 폼(`inquiryForm`)을 내린 두 근거 중
      하나가 남아 있다. `/admin/new` 직접 등록은 **같은 개인정보를 같은 테이블에
      저장한다.** 수집을 하면서 방침을 공개하지 않는 것은 위반이다.
- [ ] **마케팅 수신 동의 철회 수단이 없다.** 방침은 "동의 철회 시 즉시 파기" 라고
      적었지만 철회를 받는 창구·기능이 없다. 현재는 전화·이메일로 요청받아 수동
      처리해야 하며, 그 절차가 문서화되어 있지 않다.
- [ ] **`retain_until` 설정은 수동이다.** 계약이 체결됐는데 아무도 설정하지 않으면
      3년에 파기된다. 계약 체결 시 이 값을 설정하는 것을 **운영 절차로** 정해야 한다
      (코드로 강제하지 못한다 — 계약 체결 사실이 이 시스템에 없다).
- [ ] **상태 변경 메모(`inquiry_status_history.note`)는 자유 입력**이다. 개인정보·민감정보가
      들어갈 수 있다. 길이 제한(500자)과 화면 경고만 두었고 **코드로 막지 못했다.**
- [x] ~~**공유 ID/PW 1개**~~ — 계정·권한 분리 완료 (2026-09-10, ADR-019).
      담당자별 계정으로 로그인하면 `created_by`/`changed_by`/감사 로그에 실제 담당자가
      남는다. 역할은 `관리자`/`상담자` 2개.
- [ ] **MFA 가 없다.** 계정 분리로 책임 추적은 생겼지만 **인증 강도는 ID/PW 그대로**다.
      개인정보 조회 화면을 지키는 유일한 요소가 비밀번호 하나다. 다음 개선 대상.
- [ ] **비상 복구(환경변수) 계정은 MFA·잠금·이력이 없는 상시 관리자 경로**다.
      화면 배지와 감사 로그(`bootstrap`)로 드러내지만 **사용 자체를 막지 않는다.**
      비밀번호를 강하게 두고 아는 사람을 최소화해야 한다. 일상 업무에 쓰면 계정 분리가
      무의미해진다.
- [ ] **`session_epoch` 검증 때문에 Supabase 장애 시 DB 계정 로그인·세션이 전부 실패**한다
      (비상 계정만 동작). fail-closed 선택이지만 가용성 비용이 있다.
      이 구성의 가장 약한 지점이다. 운영 인원이 2명 이상이 되거나 접근 빈도가 높아지면
      Supabase Auth + MFA 로 이전한다. 그 전까지 **자격증명을 공유하지 않고
      접근 권한자 명단을 사내에서 관리**해야 한다.
- [ ] **로그인 잠금이 `INQUIRY_IP_HASH_SALT` 에 의존한다.** salt 가 없으면 IP 해시가
      없어 브루트포스 카운트가 동작하지 않는다(잠금 미적용).
      **가동 중이므로 지금 확인해야 한다** — `doc/10-admin.md` 6절의 쿼리로
      `admin_audit_log.ip_hash` 가 null 이 아닌지 본다.
- [ ] **감사 로그 테이블 미생성 상태로도 켤 수 있다.** 마이그레이션을 실행하지 않으면
      로그인은 되지만 감사 로그가 남지 않고 잠금도 동작하지 않는다.
      서버 로그에 기록 실패가 남지만 **코드로 강제하지는 않았다.**

### 중간

- [x] ~~**원격 강제 로그아웃 없음**~~ — `session_epoch` 로 해소 (ADR-019).
      계정별 세션 강제 만료가 화면에서 가능하다. **비상 복구 계정은 여전히 불가**
      (`ADMIN_SESSION_SECRET` 교체로 전체 무효화).
- [x] ~~**비밀번호 변경 UI 없음**~~ — 본인 변경 + 관리자 초기화 구현 (ADR-019).
      **비상 복구 계정은 여전히 환경변수 교체 + 재배포**가 필요하다.
- [ ] **비밀번호 재사용·이력 검사가 없다.** 같은 비밀번호로 되돌릴 수 있다.
- [ ] **초기 비밀번호 전달 경로는 시스템 밖이다.** 메신저로 보내면 거기 남는다.
      전달 후 삭제를 운영 절차로 정해야 한다.
- [ ] **`admin_audit_log` 보관기간 정책 미정.** 삭제 잡이 없다. 개인정보를 담지 않으므로
      (`ip_hash` 만) 급하지 않지만 `inquiries` 3년과 별도로 정해야 한다.
- [ ] **감사 로그 기록 실패가 조회를 막지 않는다.** 가용성을 택했다. 대신 `console.error`
      로 남긴다. "기록 없이 열람된" 구간이 생길 수 있다.
- [ ] 목록 마스킹은 **어깨너머·스크린샷 노출 면적 축소**가 목적이며 권한 분리가 아니다.
      같은 계정이 상세에서 원문을 본다.

### 낮음

## 절대 하지 않을 것

- `inquiries` 에 anon 접근 정책을 열기
- 주민등록번호·계좌번호·카드번호를 이 테이블에 저장
- 원문 IP 저장
- 로그·에러 메시지에 개인정보 출력
- 공개 페이지에서 문의 목록 조회
- `admin_audit_log` 에 비밀번호를 어떤 형태로든(해시 포함) 저장
- `ADMIN_*` 환경변수에 `NEXT_PUBLIC_` 접두어 붙이기
- `admin_users` 에 비밀번호를 평문·복호화 가능한 형태로 저장
- 상담자(`agent`)에게 계정 관리·감사 로그 권한 부여
- 비상 복구(환경변수) 계정으로 일상 업무 처리
- 관리자 자격증명을 채팅·이슈·커밋에 붙여넣기
